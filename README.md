# PGL · Predictive Generative Loop

**预测生成环**：一套让大语言模型 agent 与一个人长期协作的循环系统。

> *PGL (Predictive Generative Loop) is a loop system for long-term collaboration between one person and LLM agents. Three runtime systems — a work system (knowledge governance), a metabolism system (predictive memory), and a loop system (a PDSA flywheel) — are coupled through skills and run as one recursion. The file system serves as an external world model. Every night a scheduled run replays the day's transcripts, consolidates the work, reviews the plan against what actually happened, drafts the next day's plan, and metabolizes experience into reusable judgment and method. Changes to the rules enter the same loop as falsifiable predictions. This repository is the full specification, written in Chinese.*

PGL 不用数据库、向量检索或常驻进程。全部状态是磁盘上的 Markdown，全部规则也写在 Markdown 里，交给读它的 agent 执行。

系统由三个运行时部分组成：**工作系统**管知识放在哪、怎么找回来；**代谢系统**管经历怎么变成可复用的判断；**loop 系统**管从长期目标到今天的动作怎么转起来、做完怎么对账。三者不是三套并列的机制，它们通过 skill 的输入输出接口互相咬合，跑成一条闭环（§7）。规则本身也在环里：每条递归提议都登记一个预测和一个到期日，到期由后续节点按证据判命中或未中（§6.6）。把这些改动真正写进系统并部署上线的，是施工通道（§8）。

本仓是 PGL 的说明书，描述它的理论、结构、节律、判据与机械闸。可部署的运行时模板见 [PGH-dreaming](https://github.com/Hang-Yuan/PGH-dreaming)（Claude Code）与 [PGH-dreaming-for-codex](https://github.com/Hang-Yuan/PGH-dreaming-for-codex)（Codex）；模板实现了说明书的哪些部分，见 §13。

## 0 · 速览

### 0.1 三个系统

| 系统 | 英文名 | 词源 | 管什么 |
|---|---|---|---|
| 工作系统 | **Taxis** | 希腊语 τάξις，排列、秩序 | 东西放在哪、怎么找回来：分区、三层模型与预算、加载链、写入与读取管道 |
| 代谢系统 | **Metabole** | 希腊语 μεταβολή，转变、更替 | 转出来的东西怎么变成可复用的：工作固化、候选 schema、池代谢、毕业 |
| Loop 系统 | **Chronos** | 希腊语 χρόνος，时间本身 | 环什么时候转、按什么规则转：逻辑日、目标树、日 / 周 / 月节点、对账、推送 |

三个名字各取一个希腊词根的本义，所以表里保留了希腊原文。

一句话分工：**工作系统定东西找不找得到，代谢系统定经验长不长，loop 系统定环转不转。**

三者之间的关系不是并列铺开，而是首尾相接：工作日里产生的事实落进工作系统，夜里由代谢系统消化成判断，第二天 loop 系统拿着新的判断重新写计划，一天结束后再回到工作系统记录结果。三者的接缝全部写成 skill 的输入输出契约，所以任意一段可以被替换、单独测试，也可以看着接口读懂另一半（§7）。

### 0.2 递归：系统怎么改自己

三个系统都在运行中产生「这次哪里不对」的信号。这些信号里，指向规则本身的那些会变成**递归提议**——改计划怎么定、改预期怎么写、改对账怎么判。每条提议带一个预测和一个到期日，到期由后续节点按证据判命中或未中（§6.6）。

提议被采纳之后，要有东西把它写进系统、编译、部署、核验。这一层叫**施工系统（Poiesis，希腊语 ποίησις，制作）**。它在命名上和前三个并列，位置不同：前三个有自己的状态对象和运行节拍，施工没有节拍，只在系统要改的时候启动，改的对象是前三者的规则与 skill 本身。所以它是递归的**落地算子**，不是第四个运行时系统（§8）。

### 0.3 名字

- **Predictive**：系统对每一轮交互、每一份计划、每一次规则改动都先持有预测；预测与实际的偏差，加上用户的校准，驱动更新。
- **Generative**：外置世界模型持续生成，每天从新经历里生成新的状态、计划、schema 与规则。
- **Loop**：机理是闭环。日、周、月三级节点各自完成「预期 → 实际 → 对账 → 调整」；规则改动也作为预测进入环路，由后续节点检验。

PGL 的前身叫 PGH（Predictive Generative Harness System）。Harness 指承载机制的工程支架，Loop 指支架上运行的环路机理，现名以环路为所指。两个运行时模板仓沿用 PGH 旧名。

### 0.4 读法

第一次读，按 §1 → §2 → §3 建立问题、理论、全景，再按 §4 → §5 → §6 进三个系统的内部机理。只关心某一块时，从 §0.1 的表直接跳到对应章。

## 1 · 问题：长期协作缺什么

### 1.1 五项根约束

一个人与 LLM agent 的长期协作，会撞上五项结构缺失。PGL 的每一个机制都能回溯到其中至少一项。

1. **有限线性上下文。** 模型一次只接收一条有限的 token 序列，注意力随序列变长而稀释；知识与工作本身却是网络。失败形态：早期注入的身份与规则在长会话里被冲淡，压缩上下文之后行为漂移；规则引用规则、项目引用记忆的网络没有存放处。
2. **会话与运行时不连续。** 上下文、进程、设备、agent 端都会中断，状态不会自然延续到下一次。失败形态：「做到哪了」每次都要人重新交代，断点丢失，同一个决策反复做。
3. **经验不自动进入稳定参数。** 部署后参数冻结，一次校准、一段项目经验不会自己变成下一次会话能调用的结构。失败形态：同一个纠正要反复教，上周确立的偏好这周从零开始。
4. **生成期判定标准不稳定。** 同一条推理链里会出现标准滑动：判据从严到松偏移，目标从「判断 X 是否成立」滑成「为 X 找支撑」，或者标准没变、应用环节软化。失败形态：迎合立场、伪造工具输出、把工程惯性当成用户授权。
5. **多主体局部可见。** 用户、各 agent 端、各项目、各设备各持一份局部状态；共享边界、私有边界和写入权如果不显式，就会互相覆盖。

五项约束推出四类需求：外置的持久层、在有限上下文里检索网络的方法、跨会话重建状态的入口、可追溯的更新与授权。

### 1.2 现有方案的不足

常见的个人 agent 记忆方案大多只回答「记什么」：多层记忆加上「惊奇则写入」的判据。这条线有两处不彻底。

- **写入判据没有基准。** 「惊奇」要相对一个稳定的预期才有意义；没有预期作参照，不同会话的判定互相矛盾。用来指导行动的程序性脚本与用来预测用户的语义模式混在一起，毕业去向也就不清楚。
- **完全没有回答「怎么读」。** 文件之间怎样引用，agent 怎样在有限上下文里按需到达正确的知识，规则的权威源怎样不被复制体稀释。PGL 的演化史表明，这条线的缺失与第一条同样致命（§11）。

### 1.3 总立场：共建外置符号世界模型

面对这五项缺失，有一个常见的错误方向：让模型在生成时**假装**拥有这些属性，假装记得、假装连续、假装标准恒定。PGL 的立场相反：

> **缺什么，就在模型外面建什么，并且由用户与 agent 共同建。**

文件系统被当作一个可读、可写、可审计的符号世界模型。用户提供真实判断、授权和最终裁决，只有用户能判断「这条模式是不是真的我」；agent 负责抽取、编码、路由、维护和执行。每次会话从一个有限入口重建当前局部，再沿显式的网络按需读取。

外置世界模型的目标函数有五项：

| 目标 | 含义 |
|---|---|
| 连续性 | 跨会话恢复当前工作与稳定身份 |
| 权威性 | 同一事实或规则只有一个现役真身 |
| 可达性 | 从入口能沿显式边到达真身 |
| 经济性 | 完成一次判断时，读取尽可能少的无关信息 |
| 可还原性 | 能重建一个结论从何而来、何时改变、由谁授权 |

## 2 · 理论

PGL 的理论有两个来源侧。认知科学侧给出记忆的**内容理论**：值得记住的是改变预测的东西。计算侧给出信息的**形式理论**：网络状的知识怎样让一个只能线性阅读的读者用起来。

### 2.1 认知科学侧：记忆服务于预测

**核心命题：记忆的功能是支持未来预测，回放过去只是手段。** 这个立场在一手文献里的落点是 Schacter、Addis 与 Buckner（2007）的「前瞻性大脑」：大脑用存储的信息去想象、模拟并预测可能的未来事件。Bartlett（1932）的贡献在另一侧，他证明的是回忆属于想象性的重构，并非原样复现。长期 agent 维护记忆，是为了下一轮交互预测得更准：预测用户会怎么校准，什么方案会被拍板，哪类动作会越权。

由此推出记忆的形态和写入判据：

- **形态是模式（schema）**，结构为「触发情境 → 行动 / 预期」，可以直接运行；事件流水只是提炼模式的原料。
- **写入判据是「改变了预测」**。一条观察值不值得记，等价于它是否改变了系统对未来的预测。

**理论谱系。** 贝叶斯大脑假说把大脑建模为对外部世界做近似贝叶斯推断的器官，它持有一个关于隐藏原因如何生成观测的内部生成模型（可回溯到 Helmholtz 1867 的「无意识推断」，后由 Knill & Pouget 2004、Friston 2009 系统化）。预测加工（Predictive Processing）是它在算法层的具体化（Friston 2010；Clark 2013；Hohwy 2013）：高层向低层下发预测，低层把与实际观测的差距上送。

「惊奇度」在这个框架里有三个严格不同的含义，直觉式写入判据的毛病就出在把它们混用：

| 术语 | 定义 | 含义 |
|---|---|---|
| 意外度（surprisal） | −log p(o \| m) | 单次观测在生成模型下的负对数概率 |
| 贝叶斯惊奇度（Bayesian surprise；Itti & Baldi 2009） | D_KL(p(θ \| o) ‖ p(θ)) | 这条观测让信念改变了多少，即信息增益 |
| 变分自由能 | F = D_KL(q(θ) ‖ p(θ \| o, m)) − log p(o \| m) | 意外度的可处理上界（KL 项非负，故 F ≥ −log p(o \| m)） |

PGL 要捕捉的是第二种，信息增益意义上的惊奇：一条观察的价值等于它让世界模型改变了多少。Gershman（2019）提醒过一层边界：自由能原理本身没有固定的独特断言，它在不同假设组合下作出不同断言；要从中推出预测加工，还需要额外的变分近似与优化假设。

**操作化：两条轴。** 信息增益在工程上拆成两条独立可观察的轴：

- **P 轴（预测）**：观察与现有模式预测的关系，取值为命中、击穿、未覆盖。
- **C 轴（校准）**：用户是否给出明确校准，取值为正向确认、反对、纠正、中性。

写入规则只有一句：**P = 命中 且 C = 中性 → 不提取；其余组合 → 进入代谢。**

这条规则叫**默认遗忘**：默认动作是忘，写入需要 P 轴或 C 轴给出明确的价值信号。它有三处独立的根据：

1. **个案史**：Luria（1968）记述的记忆术专家 S. 意象极度生动，每个抽象概念一出现就化为具体图像，反而难以提取要点。这是一个单一临床个案（回忆性记述，机制是联觉与记忆术），不能推广成普遍结论；它只指出「记得太具体会妨碍抽象」这条方向存在实例。
2. **贝叶斯框架**：「P 命中、C 中性」的观察信息增益为零，写入它只增加噪音。
3. **容量约束**：注入预算有上限，「全记下来、事后复审删除」的代谢压力恒大于代谢能力。早期版本的候选池一周内从 17 条涨到 32 条，没有一条毕业。

**借用边界。** LLM 不能严格实施预测加工，有四处具体的差距：预训练模型的输出概率较校准，对齐训练会显著削弱校准（OpenAI 2023；Tian et al. 2023）；事实关联弥散在参数里，可以近似编辑，但单点编辑既不可靠也不可解释（Meng et al. 2022；Hase et al. 2023）；参数更新是点估计式的梯度下降，不产生后验分布；在叙事化线索下，模型倾向按代表性判断、忽略基率，显式给出概率的题型上表现较好（Binz & Schulz 2023；Wang et al. 2024）。所以 PGL 只借用「生成模型 + 偏离驱动更新」的概念结构，用一组持久参照系充当生成模型的工程替身。

这条边界是全文结构的枢纽：**预测、信念与更新无法在模型内部实现，所以必须在模型外部、在文件系统里实现。** 问题随之转移到计算侧：外置的世界模型以什么形式存在，一个只能线性阅读的读者怎样读写网络状的模型。

### 2.2 计算侧：把网络编译成线性可达的结构

两个事实之间的张力定义了计算侧的根本问题：

- **知识天然是网络**：概念引用概念，规则引用规则，项目引用记忆，身份约束行为。
- **LLM 只能线性阅读**：上下文是一条 token 序列，没有可随机访问的工作空间。

PGL 的解是全部文件治理的统一理念：

> **把网络编译成线性可达的结构，让 agent 用线性操作还原网络操作。**

沿引用边游走、查询局部子图、把更新传播到关联节点，这些网络操作被还原为几种线性操作的组合：读一个文件，检索一个锚点，追加一行。这有一个先例：语言本身就是人类把网络化认知线性化的协议，讲解者一句接一句地说，靠指代与「见上文」让听者在心里重建网络。文件系统加指针是同一个问题的工程解，PGL 把这份协议为一个没有心智空间的读者做得更严格。

还原成立需要三个条件，外加两条时间与纪律上的补充：

| 条件 | 机制 | 详见 |
|---|---|---|
| 边必须显式且精确 | 文件级加载链 + 节级锚点 | §4.4 |
| 节点必须唯一 | 单一权威源 + 指针网络 | §4.3 |
| 遍历必须经济 | 渐进式披露 + 三层模型 + 预算 | §4.2、§4.5 |
| 时间结构必须可还原 | 双链编码：状态链与推论链 | §4.6 |
| 生成期标准必须稳定 | 运行时纪律在生成前注入 | §10 |

**单一权威源是写操作的成立条件。** 更新一个节点 = 改一处本体 + 扫一遍指向它的边，这是有限、可枚举、可验证的动作。一条规则若有五份副本，一次更新就要五处同步，漏一处就埋雷。复制体会各自演化，边界矛盾悄悄累积，agent 读到哪个版本取决于加载顺序，行为就不可预测了。PGL 的一次全盘审查曾在记忆规则的 3 到 5 份副本之间查出 17 项边界矛盾：同一个阈值两种数值，同一个动作两种授权级别，同一个状态机两种语义。

**断边会静默失败。** 一个凭印象写的锚点，或者目标标题后来改了名，agent 沿边找不到节，就会用训练先验补一个；错误从此不可见。锚点可以被机械验证，才算这条边存在。

### 2.3 双系统：同一份对话里有两类信息

同一段会话转写里同时含有两类信息：**对象世界的事实**（项目推进到哪、做了什么决定）和**可迁移的预测模式**（用户在这类情境下会怎样校准）。两者的真值语义、保留判据和生命周期都不同，不能共用一套存储。

| 维度 | 工作记忆系统 | 预测性记忆代谢系统 |
|---|---|---|
| 回答 | 工作推进到哪、什么结论当前有效 | agent 学到了什么、以后怎样预测或行动 |
| 基本单位 | 状态、事实、决策、产出、推论节点 | schema：触发情境 → 行动 / 预期 |
| 真值语义 | 对对象世界的权威记录 | 对未来的候选模型，稳定性随证据变化 |
| 价值判据 | 后续接续、判断、交付是否需要 | 是否改变预测或行动，能否跨事件复现 |
| 共享边界 | 工作库，共享给用户与各端 agent | 各端私有池；稳定终态按授权进入共享身份层或本端行为层 |
| 遗忘方式 | 覆盖与归档；不因久未使用而衰减 | 默认遗忘；升降格、衰减、竞争、合并、物理删除 |
| 节律 | 节点闭合即时固化、日固化、周汇总 | 日提取、周统合、跨周稳定后毕业 |
| 权威落点 | 项目主文档、`_overview`、`_progress/`、`_current`、`weekly`、`status` | 情景池、语义池、USER、SOUL、skill、行为规则 |

两条流共享同一个证据源 L0（会话转写）：

```text
会话转写 L0
├─ 对象世界变化  → 工作固化   → 工作记忆系统
└─ 预测或行动模式变化 → schema 提取 → 预测性记忆代谢系统
```

分流问句：

1. 这条信息是否改变项目、任务或对象世界的当前状态？命中则进工作固化。
2. 这条信息是否改变对用户、agent 或一般行动模式的预测？命中则进 schema 代谢。
3. 两者可以同时命中，这时分别编码，用指针相连。

**交叉规则：**

1. 工作结论先固化，schema 代谢随后进行；schema 不达标不影响工作事实落盘。
2. schema 只保存抽象模式与证据指针，项目结论仍以项目权威源为准。
3. 项目文件可以作为 schema 的证据，私区记忆池不保存项目文件的副本。
4. schema 被击穿不会回头改写项目历史；项目的新事实走工作记忆的更新链。

**双编码示例。** 用户在某个项目里否决了方案 X，理由是「凡是依赖无法复验的中间态，都不能进生产」。

- 工作记忆编码：该项目否决 X、当前采用什么方案、依据与影响，权威落在项目主文档与 `_progress/`。
- 预测性记忆编码：如果这个判断在独立事件里复现，就形成一条候选行动 schema「生产决策要求中间态可复验」，证据指回项目节点。

### 2.4 闭环：PDSA 与自改

把三个系统串起来的是一个 PDSA 环（计划—执行—研究—处理）。

| 相 | 内容 | 落点 |
|---|---|---|
| **P** 计划 | 目标拆解与预期设定：长期 → 月 → 周 → 日 | 目标树、本周目标总表与日拆解、日段条目的「预期」 |
| **D** 执行 | 按日条目干活，产出事实 | 进展记录、执行流水、代码提交 |
| **S** 研究 | 夜跑对账：实际对预期，偏差带原因类 | 日节点回执中的偏差清单 |
| **A** 处理 | 调整次日计划、记忆代谢、递归提议 | 次日草稿、记忆池、递归登记表 |

一夜走完一圈：清晨推送给出 P，白天是 D，夜里先固化事实、再做对账，代谢消化当天并调整判断，次日清晨出新的 P。

三个系统在这个环里的分工不同：**loop 系统持有 P、D、S 三相的主要动作；工作系统承接 D 相产出的事实、并为 S 相提供证据；代谢系统承担 A 相里最重的两件事——调整判断倾向与生成新方法。** 顺序是「loop → 代谢 → loop」：代谢读刚闭合的日结果，它的出口又在下一轮 loop 写计划、做对账时自动带上。

**迭代与递归。** 迭代是环自己转：今天没做到，明天调整计划再来。递归是环改自己：改的是「计划怎么定、预期怎么写、对账怎么判」。每一条递归产物都登记一个「预测」和一个「到期日」，到期由后续节点按证据判命中或未中。改规则这件事本身因此成为一个可证伪的预测，以后可以被推翻。

**递归需要一个落地算子。** 提议被采纳之后，要有东西把它写进系统、改掉规则或 skill、编译、部署、核验。这一层没有运行节拍，只在系统要改时启动；它改的对象是三个系统本身的规则与 skill。命名上它与前三个并列，位置上是递归的执行环节（§8）。

## 3 · 全景

三个系统共享同一份磁盘。先看这张图上有什么，再看它们怎么咬合。

### 3.1 六个根

全部状态装在一个目录里，一级目录即共享边界的划分。

| 根 | 共享范围 | 内容 |
|---|---|---|
| 工作库 | 全端共享 | 对象域工作库，按区划分 |
| 主 agent 私区 | 主 agent 独占 | 该端的人格文件与记忆池 |
| 对等端私区 | 对等端独占 | 该端的人格、记忆池与演化记录 |
| 开发目录 | 共享 | 工具链开发，未上线件 |
| 发布目录 | 共享，对外 | 脱敏后的可部署模板与说明书 |
| 草稿目录 | 共享 | 人格与文案草稿 |

**私区不共享是一条硬边界。** 一端的记忆池被另一端读写，会污染该端的人格演化轨迹。跨端传信息只走通信区，不越私区。

### 3.2 工作库的区

工作库按工作类型分区，新项目进项目区开子目录，不新建区。

| 区 | 管什么 | 归哪个系统 |
|---|---|---|
| 专注区 | 当日与本周流水、目标树、活跃任务表、执行流水、推送包、审定流、归档 | loop 系统 |
| 项目区 | 全部项目本体：结论、推论链、材料 | 工作系统 |
| 元区 | 自指域：系统对自己的描述、变更留账、运行时编译源 | 工作系统 + 施工 |
| 通信区 | 跨端通信：路由表、主线、公告板、项目通信流 | 工作系统 |
| 学习区 | 学习材料与消化产物 | 工作系统 |
| 阅读区 / 写作区 | 规则在位、内容为零的待用区 | 工作系统 |
| 长期记忆 | 全局状态快照与周录 | 工作系统（loop 写入） |
| 用户档案 | 身份层：用户主档与按触发词加载的子文件 | 代谢系统（毕业出口） |
| 私区记忆池 | 情景池、语义池、代谢流水、微代谢账本 | 代谢系统 |

这张表的最后一列说明了工作库为什么不能按「谁写的」分区：同一个区会被多个系统写，写入权按文件而不是按区切（§4.7）。

### 3.3 角色

| 角色 | 主责 | 边界 |
|---|---|---|
| 用户 | 真实判断、授权、最终裁决 | 唯一能判断「这条模式是不是真的我」的人 |
| 主 agent | 判断、推演、工作库固化、记忆代谢、架构审核 | 架构审核只由这一端执行并给结论 |
| 对等端 agent | 代码工作、自端运行时、跨端执行、通信区维护 | 自有私区，不读对方私区 |
| 第三端 agent | 待议 | 未接入共享磁盘 |
| 深思席 | 复杂推理、竞争假说、反例搜索、方案审议 | 会诊输入；不直接写共享正典或任何私区 |

**sub-agent 名册**，按职能命名，两端同构：

| 角色 | 职责 | 约束 |
|---|---|---|
| 书记 | 本地文件读写、长文件落盘、归档；写入管道的落盘执行者 | 只做文件读写，不做内容判断 |
| 文献检索 | 学术文献与数据库检索 | 叶子，不做理论判断 |
| 研究者检索 | 人与机构层检索：谁在做、哪个实验室、是否开放 | 叶子，一手来源优先，不输出贴合度评级 |
| 通用检索 | 通用网页检索与对话回溯 | 叶子，不写文件 |
| 背调 | 公开信息采集 | 叶子，只采公开信息，已证与待核验分离 |
| 补跑 | 按显式指定的单个逻辑日跑完整夜链 | 唯一被授权派下级的 sub-agent；只准派书记，深度上限 2 |

派单按判断密度切线：高判断的动作（裁决、研究性写作、协议设计、回放裁决）留在主会话；重型文件读写、检索、审计派出去，只带回已经消化过的结论。把原始数据整份贴回主会话，会抵消分工的收益。

### 3.4 一天

| 时段 | 谁 | 做什么 | 落在哪个系统 |
|---|---|---|---|
| 清晨 | 投递端 | 读前夜装配好的推送包，整段转给用户 | loop |
| 白天 | 用户 + 主 agent | 按当日条目工作；节点完成即闭合；对计划的意见当场改写当日段 | 工作系统（事实）+ loop（计划呈现） |
| 白天 | 主 agent | 非中性的校准信号当场落一条情景池条目 | 代谢 |
| 夜链 | 定时任务 | 定目标日、占锁、抽转写 → 工作固化 → 目标环节点（日 / 周）→ 推送装配 → 记忆代谢 → 周 / 月转调 → 提交与解锁 | 三个系统全在 |
| 次晨 | 投递端 | 投递新包 | loop |

夜链是三个系统唯一同时在场的地方，也是它们咬合最紧的地方：工作固化与记忆代谢同源同包，loop 的对账结果又是记忆代谢的输入之一。分开写会丢掉这个时序，所以完整的步序放在 §6.3。

### 3.5 三条贯穿全系统的约束

**上下文有限。** 所有分层、预算、下沉、按需读取，都是对这一个约束的回答（§4.2）。

**会话会断。** 每轮启动从权威快照重建当前局部，不依赖隐式的会话记忆（§4.11）。

**生成期标准会滑。** 少数高风险纪律必须在生成之前就位，不能等事后审计（§10）。

## 4 · 工作系统 Taxis

Taxis 管东西放在哪、怎么找回来。

它要解决的问题是：知识天然是网络（概念引用概念、规则引用规则、项目引用记忆），而读者只能线性读。治理的全部工作，是把这张网络编译成一组线性可达的结构：从入口出发，沿显式边，一步步走到真身，读到的永远是唯一有效的那一份。

### 4.1 对象域与共享边界

工作库的六个根、九个区与各自的归属见 §3.1 与 §3.2。这里只补一条治理上的含义：**共享边界决定写入权，不决定分区。** 分区按工作类型切，写入权按文件切——同一个区会被多个系统写，所以一个文件只登记一个写入方（§4.7）。

### 4.2 三层模型：按失效速度分层

| 层 | 失效速度 | 磁盘上是什么 | 进会话入口 | 预算 |
|---|---|---|---|---|
| CANON | 永不失效 | 各区的 `00.{区域}_canon.md` | 否，写该区时由书记读 | 无 |
| INDEX | 跨周有效 | 全局状态、项目入口、公告板、路由表、区域正典自身 | 是 | 有硬上限 |
| CONTENT | 按需 | 项目正文、流水、推论链、材料、历史 | 否 | 无 |

**预算只加在 INDEX 层。** CONTENT 不占入口带宽，不限体积；CANON 只在写该区时读，也不占。入口带宽的争夺全部发生在 INDEX 层。

**同一个文件在不同层级里可以是不同层。** 项目入口文件在项目区内是 CONTENT，在项目内部却是这个项目的 INDEX，所以仍受预算约束。区域正典在多数区是 CONTENT，在元区、项目区、通信区本身却是 INDEX。这就是递归三层：Workspace 有 INDEX，每个项目内部又有自己的 INDEX，大型 CONTENT 子图还可以再建一层索引，每一级只负责判断下一跳。

现役的 INDEX 预算（字符数）：

| 文件 | 上限 |
|---|---|
| 项目区正典（全部项目的总索引） | 12,000 |
| 项目入口 `_overview.md` | 8,000 |
| 元区正典 | 8,000 |
| 通信区路由表 | 8,000 |
| 通信区公告板 | 4,000 |
| 每个项目的通信流索引 | 4,000 |
| 全局状态 `status.md` | 2,500 |
| 用户主档 | 4,000 |
| 学习区轻量线管家 | 4,000 |
| 学习区重量线入口 | 8,000 |

专注区的四个文件（本周工作台、目标树、递归登记、活跃任务表）不设总字数，但有更细的段级上限：非环流水单段不超过 600 字；环内计划段不超过 12 条、单条不超过 300 字；周复盘初稿不超过 1,500 字。推送正文另有三档：日层 600 字 / 25 行，日加周或月 900 字 / 35 行，三层 1,200 字 / 45 行。

**超预算的唯一处置是下沉**：内容搬进 CONTENT，INDEX 留一条指针。不许截断，也不许压缩措辞卡到线内。

**判据必须可机械判定。** 「不记细节」不可判定，「不超过 2,000 字」可计数。不可判定的规则只在写的人记得时才生效；而写的人往往没有动机查上限。

**预算按字符数计。** 中文文件按字节和按字符计量差约 1.7 倍，按错单位自查会误判。

### 4.3 单一权威源

同一事实、同一条规则，磁盘上只有一份真身。其余位置需要引用时，写指针，不复制正文。

违反它的后果有精确机制：复制体各自演化，边界矛盾悄悄累积，读者读到哪一版取决于加载顺序，行为不可预测。补丁只更新它看见的那一份，副本之间的差异不会报错，只会在某次执行里以矛盾的行为浮现。PGL 的一次全盘审查曾在记忆规则的 3 到 5 份副本之间查出 17 项边界矛盾：同一个阈值两种数值，同一个动作两种授权级别，同一个状态机两种语义。

修复是把网络性质恢复回来：规则本体全部收归单一权威源，其余位置降为「文件名 + 可机械检索验证的锚点」，并立下变更协议。

单一权威源同时是写操作的成立条件：更新一个节点 = 改一处本体 + 扫一遍指向它的边，有限、可枚举、可验证。五份副本意味着一次更新要五处同步，漏一处就埋雷。

### 4.4 加载链：边的表示

**文件级：加载链区块。** 每个 Markdown 文件在标题之后、正文之前，写明三件事：

- **上游**（谁加载我，在什么任务下读）：必填。没有上游的文件就是孤儿，不允许落盘。
- **管辖文件**（我加载谁，何时继续读）：有则写，无则整段省略。
- **同级联动**（我与谁互通，什么变化需要同步）：同上。

指向必须具体：路径加节名，或点名某个 skill。「前文」「本项目」「相关文件」「见上」这类泛词判不合规。反向上要求一致：A 声明管辖 B，B 的上游就必须列 A。

**节级：锚点。** 指针写成「文件名 + §节名」，把边的落点精确到节。读者不需要读一份 400 行的规则文件，只需要检索锚点文本、读命中的那一节。锚点的书写有四条硬约束：

- 锚点文本与目标文件的某个标题逐字符一致，或为其连续子串；
- 在目标文件里唯一命中；
- 写指针之前实际检索验证过命中；
- 标题不携带版本号、日期或临时说明后缀；不用步骤编号做跨文件锚点（重排即死链）。

断边会静默失败：锚点凭印象写错，或目标标题后来改了名，读者沿边找不到节，就会用训练先验补一个，错误从此不可见。锚点可机械验证，才算这条边存在。

**加载链审计。** 用脚本把上面这些判据变成退出码：

1. 每个区目录下有正典；
2. 每个现役文件声明加载链且含上游；
3. 声明的管辖目标在盘上可解析；
4. 声明的上游目标可解析（上游侧补检，此前从未被解析，死上游一直隐形）；
5. 双向一致（A 管辖 B，则 B 的上游列 A）；
6. 孤儿文件；
7. INDEX 文件不超过其正典声明的预算；
8. INDEX 文件不含 CONTENT 层标记；
9. 流水正文里的路径字面量可解析、日期段头的星期与真实星期自洽；
10. 区域正典的 frontmatter 六字段齐备、状态值合法、`zone` 与目录名逐字相等；
11. 架构文档与区域正典能否从入口走到（可达性）。

有 FAIL 即退出码非零，不得继续，也不得自行放宽验收标准。存量 FAIL（不是本趟写入造成的）可以登记到待裁项、写明清偿排期后继续，排期到期未清即停机。

**审计器自己会假绿。** 脚本的三种隐蔽错法：检查器缺来源，造出成片的假红；前置条件把断言吞掉（产物目录不存在就直接返回通过）；硬编码指向已删的文件。所以对审计器本身也有回归测试，每修一次闸就加一条针对该假绿形态的用例。设计检查时先问一句：如果被检查的东西现在就是坏的，这个检查会不会输出任何东西？答案是不会，它就不是检查，是安慰。

### 4.5 渐进式披露与索引预算

每一层索引只携带「足以决定要不要进下一层」的信息。入口文件只放最小宪法：足以稳定系统行为的最少规则；具体流程下沉到 skill，证据与历史下沉到日志，身份层只接收毕业结果。

推荐的节点载荷：作用域、当前状态或结论摘要、权威来源、子节点覆盖、进入条件、停止条件、不确定性、精确指针。

这套做法的成本收益有实测：入口文件从 410 行收到 217 行，常驻词元减半，规则的权威源反而更清楚，因为每条规则从「散在三处」变成「一处本体加两处指针」。

预算只约束体积，不保证摘要足以决策。一份长度合规的入口仍可能让读者必须逐份打开才敢选择——这是渐进式披露的验收缺口（§10）。

### 4.6 双链编码

工作过程同时记录两条链：

- **状态链**（what / when）：发生了什么、产出是什么、当前状态怎样。落点在当日流水、周录、全局状态快照、项目入口的当前状态。
- **推论链**（why / how）：判断依据、替代方案、转向、开放问题。落点在项目的推论链目录。

两条链用稳定编号或锚点互引。从任一结论能回到依据与证据，从任一推论节点能找到落地产出。

推论链的节点有固定骨架：问题、推进、结论、新问题、详记指针，五字段缺一即不合规。节点之间以「开出的新问题」串起来，形成一条可回溯的问题链；详记下沉到展开子文件，论证展开不进骨架。

推论链的展开子文件有质量红线：节与节之间要写桥句——上一节留下什么缺口、为什么必须用这一节补、这一节的什么能力正好补这个缺口。只贴标签的导览是失败的导览。

### 4.7 写入管道

写入分三段，主 agent 不直接落盘：

```text
主 agent   →  写入载荷：目标文件 / 目标节 / 层级 / 内容要点 / 关联指针
书记 sub   →  读目标区正典取规则 → 按 skill 流程写 → 跑加载链审计 → 回执
主 agent   →  一重审核（回执 vs 意图），不复读全文
```

载荷里不含格式；格式是正典的职责。

**书记的三道闸**，超一条即拒写并回报应下沉的去向，不得自行放宽：

| 闸 | 判据 | 判法 |
|---|---|---|
| 层级匹配 | INDEX 层不得出现 hash、版本号、测试数或文件数、绝对路径 | 四条正则扫描；扫描前剥掉代码块与加载链节 |
| 预算 | 写入后总量不超过该区正典声明的上限 | 计数，含拟写内容试算 |
| 格式 | 符合正典模板：节名、表格列、一项目一行 | 逐条对模板核 |

**例外只有两类**：当日工作台的单行追加；审定流里用户原话的逐字转录单行追加。INDEX 层与身份层没有例外。

**写入方分区。** 每个项目只有一个写入方，登记表只登记「写入方不是主 agent」的项目，未登记即主 agent。非写入方要改，在该项目的通信流发提议：稳定键、目标文件与节、拟写内容、证据指针；写入方整合后以同一稳定键回执。四个写入类 skill 在落盘前都查这张表。

**覆盖需要收据。** 项目主文档的结论节是覆盖写。覆盖是破坏性写入，产物本身看不出被替换了什么，所以每次替换都写一份覆盖收据（键、旧值摘要、新值摘要、目标日），由次日首个会话报给用户。收据缺失而本轮覆盖数大于零，当场拒写。

**物理层的保留规则。** 按「能否从上游重建」分四类：原始采集数据不入同步，本机保留并记来源与哈希；归一化产物入同步、长期保留；中间分片与解压件在对账通过后即删；依赖目录随时可重装。删除中间件之前必须做三方哈希对齐（分片拼接值、目标件、收据记录值），对不上一律停手上报。

### 4.8 读取管道

逐层下沉，每层读完判断要不要再下沉：

```text
<项目>/_overview.md  →  [判断]  →  <子项目>  →  [判断]  →  _progress/  →  节点文件
```

需要全局视野时从全局状态进：全局状态 → [判断] → 项目入口。一次读到底，等于把 CONTENT 层灌进入口带宽，分层就失效了。

超预算的文件派 sub-agent 读回摘要；主 agent 只拿结论，不背原文。接续与汇报的读取顺序固定为七层：全局状态的现状行与相关待裁项 → 项目或子项目入口 → 最新的推论链节点 → 项目通信流尾部（不足则沿索引读历史卷）→ 迁移期兼读主线与公告板 → 今日推送条目 → 对等端今日执行流水。每层没有内容写「无」，不脑补；汇报的每一行都要能指回某一层。

### 4.9 项目生命周期

**成立三条件**：独立推论链、独立交付物、独立权威根（自己的入口文件）。三者齐备才算一个项目；缺任一条，它是某个项目的子结构。目录或话题本身不自动取得项目地位。

**数量闸**：任何单层目录下并排的项目超过 7 个，就必须加一层容器，或归档一个。臃肿感来自同层并排的数量，与总量无关。

**合并与拆分**：两个项目共享同一条推论链、且其中一个没有独立交付物，合并；一个项目里长出两条互不依赖的工作线、各有独立交付物与对外赛道，拆分。两个动作都要同轮更新总索引、跨项目授权表与全局状态，并在变更日志留账。

**建项目流程**：一次问清七要素（名称、目标、关键人物、当前阶段、项目类型、线归属、是否需要跨项目引用），缺项留空不由模型填补；落点判定（是否同名、归哪个容器、顶层是否已满 7 个）；建入口文件（含加载链、当前状态、断点与下一步）；登记总索引；判断跨项目互通（需要时先裁决再写三处：本项目关系节、对方关系节、授权登记表）；交棒给推进记录与文献管理。建到入口落地并同步总索引即终点，不预建空目录。

**项目目录的三级串联**：

| 级 | 文件 | 职责 | 不该有 |
|---|---|---|---|
| 项目索引 | 入口 `_overview.md` | 整体到哪了、子项目清单、权威文件指针 | 逐日流水、推论链 |
| 项目推进 | `_progress/` | 串子项目：哪条线到哪了、线之间什么关系 | 单个节点的材料本体 |
| 子项目推进 | `<子项目>/_progress/` | 串节点：该线的节点序列与因果链 | 与这条线无关的内容 |
| 节点 | 具体文件 | 推论链、材料、代码、数据 | — |

判据：一个容器要同时描述两条互不依赖的工作线，它就是「串子项目」层；只描述一条线的时序推进，它就是「串节点」层。单项目没有子项目时直接串节点，不为形式补一层空壳。

**两套索引分工。** 项目总索引按磁盘目录取真值，表行数必须等于发现数，状态五值：活跃、维护、休眠、收尾、已归档。全局状态的「项目现状」管的是另一个集合：当前有推进意图的条目，允许跨区，是注意力清单而不是目录清单。两表条目数可以不等，差异必须声明，否则「少了一行」分不清是漏记还是按定义不该在。

**归档**：整理产出清单 → 与用户对齐是否还有悬置点需要单独迁出 → 整体移入归档目录并保持目录结构完整 → 标只读 → 永不删除（归档替代删除）→ 同步总索引。大批量历史搬运按字节级复制，不经解码再重编码；写完做严格 UTF-8 解码并统计替换字符数，必须为 0。

### 4.10 通信区

通信区是跨主体的传输、路由、交接与收据层。项目结论、推论链、全局状态与私区 schema 各有权威源，通信区只保存消息与交接历史，用精确指针指向真身，不保存项目结论的副本。

**结构**：本区正典、路由表（索引）、当前主线（只追加）、常驻公告板（状态快照）、按项目分的通信流、诊断收据、归档。

**路由**：一个已登记项目对应一条项目路由，按实际通信需求懒注册，不为全部项目预建空目录。路由标识与项目路径分离：项目移动只更新映射，历史消息里的标识不变。一条消息只选一个主路由，相关路由留指针。

**消息**：标题行写时间、来源、对象；下一行一个稳定键；正文。新消息一律追加到文件末尾，严格按时间从上到下，不插入中段。修正旧结论时追加新段落并声明「以本条为准」，不改写对方原文。同一条事项的回执复用原稳定键。单条消息不超过 1,500 字，超长的正文落进该路由的任务包目录，流里只放摘要与入口。

**回执粒度**：流里只发需要对方行动的请求、阻塞或风险变化、阶段结论和最终交付；逐项测试结果、重复状态、文件指纹明细进任务包。同一稳定键同一逻辑日的普通中间进展合并成一条阶段汇总。没有下一动作的「已看到」不追加。同一事实跨路由只留一份正文。

**轮转**：项目流达到 800 行或 60,000 字符（任一即触发）整卷归档，保留原文字节、原行号、消息时间与稳定键，当前卷保留加载链并写上一卷指针。写入统一经过一个维护脚本（审计、追加、轮转三个命令），追加前校验路由已登记、标题格式、恰一条消息、稳定键在位、正文长度、消息时间不早于当前末尾；写入走原子替换加文件锁；每次先落意图收据，校验后改验证收据。

**公告板**是状态快照，过期即删，不留流水，只放现役有效的路径表、生效协议、跨端状态与待接任务指针。它不是权威源：信息要进身份层或记忆系统，仍须走对应流程。

### 4.11 派单

名册与各角色边界见 §3.3。派单在治理上的约束只有一条：书记是写入管道的落盘执行者，不做内容判断；其余检索类 sub-agent 是叶子，只带回消化过的结论。

### 4.12 启动序列

**触发**：上下文中没有身份层痕迹时，必须先完整加载必须层再响应。身份层由会话启动 hook 直接注入，不重复读；若这一轮的上下文里没有同时出现两份身份文件的正文，视为 hook 缺失，必须先显式读它们，不得因为「预料 hook 在」而跳过。

解析出的顺序是三层：

1. **必须层**：身份层（用户主档与 agent 人格，合计不超过 6,500 字），加上会话自检。
2. **按需层**：全局状态、周录、本周流水、公告板、项目入口与推论链、身份子文件、区域正典、私区记忆全文——每一项有自己的触发条件，不预读。
3. **会话自检**：只判两件事——昨夜事务是否闭合、今日推送的提交回执是否在位。正常时无输出；异常时每项一行、以告警符开头；脚本恒返回 0，不让会话因为检查中断。

**进入工作的路由**：用户点名项目 → 读该项目入口，需要细节再沿读取管道下沉，不预先汇报全局进度；问进度或说「继续」而未点名 → 调续接 skill，由它路由；只为某件具体事 → 直接做，不套工作流报告；打招呼或闲聊 → 自然回应。有告警时开头一句话说明缺什么、要不要补，不展开内部字段。

## 5 · 代谢系统 Metabole

Metabole 管转出来的东西怎么变成可复用的。

它的原料有两份：当天的全部会话转写，和当夜对账留下的回执。它的产物是一组可运行的预测单元：`触发情境 → 行动 / 预期`。这些单元随时间衰减，只有被反复证实的才逐层上行，最终毕业成身份层的一部分，下一次会话启动就带着它出发。

**默认动作是遗忘。** 一条观察要进入系统，需要它改变了预测，或者用户给出了校准信号。记下来的是少数。

### 5.1 两套系统，两种寿命

同一段会话里同时存在两类信息，它们的寿命完全不同。

| | 工作记忆 | 预测性记忆代谢 |
|---|---|---|
| 回答 | 工作推进到哪、什么结论当前有效 | 学到了什么、以后怎样预测或行动 |
| 基本单位 | 状态、事实、决策、产出、推论节点 | schema：触发情境 → 行动 / 预期 |
| 真值 | 对对象世界的权威记录 | 对未来的候选模型 |
| 保留 | 保留到被新结论覆盖或项目归档 | 默认遗忘；升降格、衰减、竞争、毕业 |
| 遗忘方式 | 覆盖与归档 | 衰减、合并、物理删除 |
| 节律 | 节点闭合即时固化、日固化、周汇总 | 日提取、周统合、跨周稳定后毕业 |

工作记忆不衰减：一个项目的结论不会因为三个月没被引用就自己消失。预测性记忆默认衰减：没被再用过的候选模式会被删，删掉才是健康状态。

### 5.2 三层加一个源

| 层 | 载体 | 启动注入 | 职责 |
|---|---|---|---|
| **L0** 只读源 | 宿主的会话转写文件 | 否 | 当日全部对话的原始记录，零维护、完美保真，夜链回放的唯一输入 |
| **L1** 情景池 | 情景记忆文件 | 否 | 1–3 星的候选 schema，四态：活动 / 复审 / 候补 / 休眠 |
| **L2** 语义池 | 语义记忆文件 | 否 | 4–6 星、能预测未来行动的稳定 schema，含活跃组与毕业候选 |
| **身份层** | 用户档案、agent 人格、行为规则、skill | 是（白天的底座） | 毕业的终点，只接收剥壳后的稳定描述 |

**命名借用。** L1 与 L2 借用 Tulving（1972）情景记忆与语义记忆的区分，用来说明「事件性」与「抽象性」两类模式的性质差异。L0 是工程基座，Tulving 的分类里没有对应物；PGL 的语义池容量受限，Tulving 意义上的语义记忆没有容量上限。目标是工程代谢，不做认知建模。

#### 5.2.1 L0 的边界

L0 只是输入。系统按三条规则决定读什么：

- **按逻辑日取窗口**：只读目标逻辑日窗口内的记录。
- **只收人类回合与 agent 回复的文本部件**：工具结果、思考块、工具调用记录属于实施流量，不进回放。
- **会话必须有窗口内可见的人类回合**：独立排程跑本身不含人类回合，整份排除，否则夜跑会代谢自己前一夜的产出。

抽取范围要覆盖三类容易被漏掉的内容：

- **对话中途插入的话**。用户在一轮生成过程中打进、当轮被吞掉的消息，在落盘记录里是附件形态。只收「用户 / 助手」两类回合的抽取器会把这类原话整批漏掉；系统从落盘记录的附件类型里把它们重新收回人类回合。
- **跨端转达的消息**。其他 agent 的消息以独立标签收入，永不计入人类回合，也不作回放锚点。其中转述的用户决定不能直接当原话采信：须「原话、原话时间、来源会话」三项齐全，才按审定流的转达规则处理；缺任一项只按事实并入候选，记「待本人确认」。
- **内部记录**。系统注入的提示、压缩摘要、技能正文、任务通知，一律不可见。

**去重**跨会话存储根进行：同一会话可能在多个根下各存一份，只扫一个根会静默丢掉大半日内容。两边都扫，按「会话、轮次、角色、文本哈希」去重，同一句人类文本在 300 秒内出现两次只留最早一条。

**人名正名**：回放前读一份人名别名表，人名一律写正名，原文锚点保留原写法。转写误识别是常态，不正名就进池，之后每个会话都照着错的名字理解人。

#### 5.2.2 锚点切片：把转写压到能放进上下文

整天转写远超上下文。系统只装以用户原话为锚点的三段：锚点前助手最后一段正文、锚点本身、锚点后到下一个锚点前助手这一轮的最后一段正文。每段首行带源文件与行号，需要更多上下文时按行号回原文取。实测下来，消息数从 165 条压到 35 条，体量约减半。

抽取器报错时退回全量模式，并在账上记一行「锚点抽取失败，退回全量」。

**分片**：单块上限默认 50,000 字符（下限 4,000），按行切、超长行硬切，片号四位补零。每片带片头与运行标识；索引文件逐字列出片号、路径、哈希与字符数。

运行标识由目标日加转写全文哈希、再加抽取配置指纹得出，配置一改标识就变。同一内容重抽，幂等保留原收据；内容不同、又要重抽，须显式强制，并把前一份整目录搬进归档子目录、写一份取代溯源（谁取代了谁、何时、当时收据状态），永不原地删除。

#### 5.2.3 零会话日是合法的一天

目标日没有任何会话时，判据取四个读数：会话数 0、消息数 0、错误清单为空、窗口已闭合。四项全真才走零会话日闭合路径，任何字段缺失按假处理。

这时省掉回放与两轴判定，收通信区、节点段、推送装配照跑，链照常闭合。否则排程每晚都会返回同一个最早未闭合日，夜链原地踏步。

### 5.3 phase A：工作固化

phase A 把转写里的对象世界事实落进工作库。

#### 5.3.1 幂等

判据是 phase A 自己的收据存在、且日期等于目标日。只有 phase A 在流程末尾写这份收据；写早了，中途失败的一趟次日会被判「已固化」而整段跳过。

不能用「当日流水段是否存在」当判据：节点闭合流程写同一个位置，当天闭过任一节点就会让整段 phase A 跳过，剩余工作永久漏固化。一天多节点是常态。

差分的粒度是候选条目，不是整天：已固化的跳过重写，新增与修正照写。

#### 5.3.2 路由

| 内容类型 | 落点 | 写法 |
|---|---|---|
| 节点结论 | 项目主文档本体 | 幂等键整条替换；每次替换写覆盖收据 |
| 推导过程、逻辑转点、辩论记录 | 项目的推论链目录 | 追加 + 跨日回读；昨日判断今日被推翻时，在昨日那条后标「已修正，见今日段」 |
| 跨周状态变化（项目现状、主次矛盾、待裁项） | 全局状态文件 | 一项目一行；索引层禁 hash、版本号、测试数、绝对路径 |
| 周级推进（从 X 到 Y） | 长期记忆的本周节 | 每项目一行 |
| 实质工作产出流水 | 当日工作台的进展记录 | 按日段追加，结论只放指针，单段不超过 600 字 |
| 人员事实（谁在团队、职位、入职离职、名字写法） | 用户档案的人员表与别名表 | 只认本人原话；其他来源只列待核。事实型条目不进池、不评星、不走毕业 |
| 架构 / 协议变更 | 版本化变更日志 | 不进记忆账本 |

**覆盖纪律。** 项目主文档的结论节是覆盖写。覆盖是破坏性写入，产物本身看不出被替换了什么，所以每次替换都写一份覆盖收据（键、旧值摘要、新值摘要、目标日），由次日首个会话报给用户。收据缺失而本轮覆盖数大于零时当场拒写：覆盖刚发生时旧值还在手边，是唯一还能正确补写的时刻，提交时补写等于编造旧值。

**写入方闸。** 落点属于另一端登记的项目时，本端不写，改发该项目的通信区提议（稳定键 + 目标文件与节 + 拟写内容 + 证据指针），同键在位不重复追加。索引层没有直写例外，一律由书记 sub-agent 过三闸（层级 / 预算 / 格式）后写入。

**收尾三检**（收据之外）：收据声明的落点文件修改时间必须晚于占锁时刻；有推论链目录而没有项目主文档时，回候选清单复判是否漏了节点结论；收据本身不得早于全部落点。

#### 5.3.3 白天也照样写工作库

白天写工作库不受记忆池的任何边界约束：节点闭合时固结论、进度行、白天纠偏改计划，都是工作库写入。这句话之所以要写出来，是因为「白天零记忆写入」这个旧提法容易被读成「白天什么都不写」。记忆池与工作库是两回事。

### 5.4 phase B：记忆代谢

phase B 把转写里的预测性信号变成候选 schema，并决定哪些上行、哪些留下、哪些删掉。

#### 5.4.1 差分对象

两轴判定是一次差分，基线是现有 schema 的全集：

| 基线 | 比对什么 |
|---|---|
| 情景池 | 是否命中已有候选 → 升星；是否同构 → 合并；是否命中休眠态 → 唤醒 |
| 语义池 | 是否命中跨情景 schema → 强化；是否被击穿 → 标修订。两池退注入之后，代谢期是语义池唯一被读取的时机 |
| 身份层 | 命中 → 不加权（已毕业的不重复强化）；击穿才是身份层待更新的信号 |
| 用户档案的子文件 | 判「未覆盖」时另行检索其标题，指向同一模式则改判命中 |

主文件不进归档比对，归档只存证据；skill 不进基线（它是已毕业的程序型终态，走独立的审改流程）。

#### 5.4.2 两轴与过滤

- **P 轴（预测）**：命中 / 击穿 / 未覆盖。
- **C 轴（校准）**：正向 / 反对 / 纠正 / 中性。

过滤下限：**命中 + 中性 → 不提取**，其余组合进代谢判定。

三处例外：

- **命中 + 正向**要提取，但只对尚未命中身份层的 schema 生效。终态再确认也不动它；中间态靠不断确认往毕业爬。
- **身份层前置过滤**：先看命中哪一层。命中身份层且校准是中性或正向，不提取；校准是反对或纠正、或预测被击穿，进代谢判定，但不直接改身份层。命中语义池且校准中性，不提取。
- **候补态例外**：命中候补条目时，过滤只决定提取次数；状态迁移看命中的事件是否与创建事件相互独立。

**判决要可复核。** 每个信号写一行判决：信号、证据锚点、P、C、命中层、命中锚点、动作、理由。收据通过校验即冻结；命中锚点必须在被指名的权威文件里恰好出现一次；判「未覆盖」的行不得写命中层与锚点。落盘后自查出分歧，更正写进账本的勘误节，不回写收据。

#### 5.4.3 抽象红线与 schema 的成立判据

一条候选要成立，两件事同时满足：形式达标（触发情境 → 行动 / 预期），且跨事件抽象（两个及以上不同事件支撑同一类情境）。

- 单事件换个句式不算抽象；同一节点对同一事件的多次提及不算两个独立事件。自检方法：只看这一条单事件证据，能否写出这条 schema —— 能，就是换句式；不能，才是跨事件抽象。
- 单事件直升活动态只允许四类高风险：越权、系统事故、重大安全信号、以及必须当场记下的强信号，且须写明复审条件。
- **能画出一个「不这样做」的真实对照人，才算 schema。** 画不出来，这条模式就塌成全称重言式（「做对了事就能做成事」之类），不升；已经升的降回去。事实本身不是 schema：只有会改变未来预测或行动的模式才进系统。

#### 5.4.4 情景池：状态、星级、衰减

字段：强度、状态、类型（程序 / 语义 / 混合）、语境（跨情景 / 项目语境）、创建日期、最后激活、提取次数、触发情境、行动模式、预期、来源指针。

**状态机四态：**

```text
候补（单事件）── 第二事件 ──→ 活动（≥2 独立事件）
活动 ── 7 有效工作日无激活且提取 0 ──→ 复审 ── 到期 ──→ 物理删除
活动 ── 升★达标 ──→ 升入语义池
复审 ── 再激活 ──→ 活动
休眠（项目语境条目停工降级）── 回放命中 ──→ 唤醒（保留星级）
```

**升星：**

- 同一日再次校准只计 1 次。
- 7 个有效工作日内再次校准 +1 星。
- 8 周内复发（被校准）3 次及以上 +1 星，不受 7 个有效工作日的间隔限制。
- 被明确击穿：重写三件（触发情境、行动模式、预期），或新建一条竞争候选。
- 跨情景条目已到 3 星再被命中：不直升语义池，提取次数 +1，并标「待统合簇」，留给周段统合。
- 追溯命中（补旧账）只记痕迹，不计强度，也不进复发计数。

**衰减是纯机械的，N 级自治，提取次数达到 2 即免疫：**

| 条件 | 动作 |
|---|---|
| 7 个有效工作日无激活且提取 0 | 活动 → 复审 |
| 提取 1 次、14 个有效工作日无再激活 | 活动 → 复审 |
| 复审且提取 0，累计 14 个有效工作日 | 物理删除 |
| 复审且提取 1，累计 21 个有效工作日 | 物理删除 |
| 候补 7 个有效工作日无第二证据 | 物理删除 |
| 提取 ≥ 2 | 不按时间自动删 |
| 提取 ≥ 5 | 复审是否应合并进语义池或项目规则（提示面，不拦闸） |

复审观察期恒为 7 个有效工作日；删除阈值等于该提取档的转复审阈值加 7。所有阈值读「最后激活」之后的总有效工作日寿命，转复审不另起时钟。

**有效工作日**的定义是：当天工作台的进展记录有流水追加。纯对话日不算。

**执行者分工**：周段是时间衰减的唯一执行者；每日 phase B 只顺手做候补到期删，平日不处置逾期的活动与复审条目。挂在未闭待裁项下的条目免时钟处置，记豁免，裁决闭账后豁免自动失效。

**容量**：

| 池 | 健康线 | 预警 | 硬线 |
|---|---|---|---|
| 情景池（活动 + 复审） | ≤ 30 | 30–40 | > 40：当轮必须清到 40 以内，周段用同一算法复跑，两处都拦提交 |
| 候补态 | ≤ 10 | 超线即信号洪水，只提示 | — |
| 语义池活跃组 | ≤ 5 | 6–7 无动作 | ≥ 8 预警可退；≥ 10 必须强退 |
| 活跃组内项目语境条目 | ≤ 3 | — | 硬限 |

休眠态不计容量，季度出清。

#### 5.4.5 容量强制清理：机械规则，没有裁量

触发条件是情景池的活动加复审超过 40 条。目标是清到 40 以内，清理条数等于当前条数减 40，只清到刚好不超线。这条规则不询问、不挂待裁项、不进确认级。

**排序键（字典序）：** ① 提取次数升序（0 先）→ ② 星级升序 → ③ 最后激活升序 → ④ 标题字典序决胜。

**保护层**（不参与排序、不删）：提取 ≥ 2 且 3 星；标题在未闭待裁项内；休眠态；当日新建的候补转活动条目；纠偏类条目（在池至多 8 条，超出部分按原键参与清理）。

**执行顺序是一条硬约束**：先往账本当日条目写明细（编号、标题、删除键三元组），确认写入后才物理删除。同一个池跑两次必须删同样的条目，禁止「随机」或「挑最不重要的」这类不可判定的表述。先删「从未被回放」的条目是唯一可辩护的顺序：提取次数是这条记忆有没有真被用过的唯一现成计数，星级只反映写入时的判断。

#### 5.4.6 语义池：升格、统合、衰减

字段：强度（4–6 星）、状态（活跃组 / 备用 / 需要修订 / 毕业候选 / 已毕业）、类型、语境、预测情境、行动预期、证据指针。主文件写得很简，证据全在归档里。

**升格判准**（逐条过）：

1. 能写成非机械的「预测情境 → 行动预期」。
2. 跨日、跨节点或跨情境复现（重大安全信号可以单条，须注复审条件）。
3. **领域无关性分流**：抽掉项目名、理论名、具体对象，换一个不相干项目仍成立 → 跨情景，走慢轨；不成立但满足项目语境快轨 → 项目语境，走快轨，强制标注项目名；两者都不成立 → 不升。
4. 对照人测试：能画出一个「不这样做」的真实对照人。
5. 逐条判，不批量过。
6. 有 P/C 证据。
7. 不与身份层、主文档、周录冲突。
8. 能抽象到比当下证据更深一层的内在稳定模式。形式达标而这一条不达标，属于机械搬运。

**项目语境快轨**：同一项目累积 3 个有效工作日复现且过判准，走日级升入语义池，不经周段那道唯一的门，强制标注项目名。之后积累到跨项目命中，可以摘掉标注转正。衰减到 3 星时回写情景池的休眠态；跨情景条目则回活动态。

**横向统合**（周段，N 级，跨情景情景池升语义池的唯一门）：

1. 按深层结构聚类，不按措辞；优先纳入「待统合簇」。
2. 逐簇析出母结构，母结构须过升格判准。
3. 母结构与证据先落盘，确认后才物理删除贡献条目。
4. 防过度合并：再合并一次就画不出对照人时即停。
5. 不成簇的单条够格可以直接升。

日级的 3 星再命中只标怀疑，不做升格判断：单条纵向反复命中只能证明它自身稳定，证不出它是不是某个尚未成形的母结构的单一表面，判断需要全表在场。

**语义池衰减**：整周无命中降 1 星；被击穿并纠正标「需要修订」，周段重写或降级；降到 3 星移出活跃组，回写情景池；6 星且跨周稳定，生成毕业候选。

回写记账分两种：无命中降星、满额强退，提取次数记 2（免疫下限）；击穿后降级记 0，按未验证重新计时。

**合并、竞争、删除三条去向**：深层结构同一，升星不新建；疑似同构，标「待统合簇」留到周段；被击穿，重写或新建竞争候选。删除只走三条机械通道（时间衰减、容量清理、季度休眠出清），每条都先固化后删。

### 5.5 毕业

毕业是模式离开候选池、进入身份层的过程。它决定了「下一次会话一开始就带着什么」。

#### 5.5.1 条件

毕业线：6 星 + 跨周稳定不少于 3 周 + 裁决。高风险纪律可以在 6 星 + 2 周时提出候选，仍需裁决。项目语境条目不毕业，须先摘标转正。

裁决人按写入授权：一端由用户裁决；另一端由主 agent 按常设授权在事务内裁决，解锁之后执行。

#### 5.5.2 判型分流

按「条目主体是谁」分流：

| 主体 | 出口 | 约束 |
|---|---|---|
| 用户本人（语义型） | 用户档案，唯一出口 | 四件套写全：机制句、世界观假设、触发情景、预测动作；蒸到根要挖出世界观假设，检验方法是反事实反转（假设反转，行为必须跟着反转）；情境绑定的不进 |
| 团队成员或外部协作方（事实型：这个人是谁） | 人员表与别名表 | 不进池、不评星、不走毕业；当夜直接写；冲突以晚的原话为准 |
| 团队成员或外部协作方（语义型：这个人在某类活上的表现） | 工作库的协作方观测记录 | 两个及以上独立事件；证据来自回执与对话；禁止作为对人的整体评价进入任何身份层文件；也不写 skill（它约束派遣判断，不是执行方法） |
| 主 agent 自身（行为与关系层） | 本端人格文件 | 同四件套与时间判准 |
| 程序型 | 四出口决策树 | 按序判定，命中即止 |
| 混合型 | 语义面与程序面拆开各走各口 | 允许不同时毕业 |

**程序型四出口**按序判定，命中即止：

1. **hook**：触发可代码化、动作确定。脚本不超过 30 行，单一判定加单一动作；超线说明蒸馏没到位，退池。须经沙盒实测。
2. **本端人格文件**：人格层与关系层的模式，四件套格式。
3. **skill（已有对应 skill）**：五条全中——多步有序（不少于 3 步，前一步的产出是后一步的输入）、至少一个可落盘的中间产物、至少一处需要判断的分支、领域绑定、可重入。最容易被放过的是中间产物：没有中间产物的「多步」实际是脑内一串动作，写成 skill 会变成没人照做的说明书，退池。
4. **skill（无对应 skill）**：登记蒸馏候选，三路独立蒸馏收敛后交元技能成稿并部署。
5. **入口文件的行为规则**：全局、需模型判断、高频；单条不超过 80 字，一次毕业至多 1 条；写不进 80 字说明没蒸熟，退池。

#### 5.5.3 蒸馏、实测与写入

- **三路独立蒸馏**：并行拉三个互不可见的 sub-agent，各拿「条目原文 + 全部证据 + 出口规范（含字数约束）」，独立产出。三路一致进下一道；两路一致取多数决并标分歧点；三路各异判未熟，退池继续攒，当次不生成提案。
- **hook 实测**：收敛版先存暂存区，全程不触本端配置、不进 hooks 生效目录；再并行三路各自设计测试集（应触发 / 不应触发 / 边界）在沙盒实跑，三路全过（应触发全命中、不应触发零误伤）才升「已验证」。
- **流程**：周段只生成候选 → 账本留账 → 裁决 → 写前剥壳（去星级、去临时证据、去现场情绪、去重复来源，只留稳定描述与必要边界）→ 写入 → 语义池条目标「已毕业」并移出活跃组 → 审计并归档。
- **事务内不写身份层**：身份层写入排在释放锁之后。夜间只做「已毕业候选的收尾」（标已毕业、移出活跃组、写归档、写账本），依据是两项证据：当夜转写里的裁决记录，与目标文件在目标日的实际变更。缺任一项，该条留在活跃组并点名缺哪项。

#### 5.5.4 程序记忆分支

程序型条目另有一路输入，来自「流程情景」：

- **流程情景**是记录单位：把当天完整跑过的一套流程记成一条情景，挂在对应程序型条目的来源指针下。字段包括触发领域、触发时点与对象、是否调用了现役 skill、实际步骤、偏离（补做 / 跳过 / 改序）、落盘的中间产物、出错的步骤、环境预测误差。
- **登记蒸馏候选**须三条同时成立：同领域情景累计 3 次及以上；涉及 2 个及以上不同对象；该领域没有现役 skill。候选按情景次数判，与条目星级无关。三路蒸馏不收敛说明流程尚未定型，候选保留，下次同领域情景入池后重蒸。
- **该用没用**：领域已有现役 skill 而情景没调用它，在该 skill 名下记一次。
- **偏离写回**：同一处偏离或同一个出错步骤在两个及以上情景出现，按「已有 skill」那一出口写回该 skill 的管辖节。
- **环境预测误差**（五类，作为 C 轴的另一种校准）：流程产出之后测试由绿转红；被加载链或同类审计判 FAIL；回写或编译被判漂移、或被写入闸拒写；交付晚于承诺截止日；产出之后被本人或团队成员改判返工。按 P 轴判：提前预言了这次出错 +1 星；照做仍然出错算击穿，重写或新建竞争候选；没有条目覆盖记「未覆盖」，进情景池。

### 5.6 白天的边界

「白天零记忆写入」在现役系统里已经不成立，准确的边界是三条并列的规则：

**白天零批量代谢。** 不做两池全量代谢。全量是关键词。

**白天零批量注入。** 两池默认不进上下文。白天共同世界模型的底座是三件套身份层：用户档案、agent 人格、入口文件的行为规则。

**白天有两条受控的写入口：**

- **节点级直升**：节点闭合时，两个及以上独立事件支撑同一类情境，或单条高风险、越权、系统事故并注明了复审条件，可以直接写进情景池的活动态。天花板是活动态，不碰语义池与身份层。
- **即时微代谢**：会话中出现非中性的校准信号——校准轴判为反对或纠正，或用户给出改变后续行动的明确指令——当场判两轴，落一条情景池条目（单事件落候补态），或对深层结构同一的既有条目升星。约束四条：只写情景池；每逻辑日新建至多 5 条，超出留到次晨全量回放（升星不计入上限）；情景池进红区时只升星不新建；夜链持锁期间不写。每次写入向当日的微代谢账本追加一行，作为次晨对账凭据。
- 次晨 phase B 在判决过闸之后、毕业候选收尾之前，逐条复核前一日微代谢写下的条目：维持、修正（轴判错或独立事件计数错）、合并（与当日回放出的同结构条目重复），结论并入当日账本。会话里漏掉的信号仍由全量回放兜住。

**语义池白天零写**：写者只有日级 phase B 与周段。

**纠偏的窄注入**：从情景池派生一份纠偏摘要，只收最近 7 个逻辑日内、来源是白天纠偏行、且处于活动或复审态的条目，至多 8 条、全文不超过 1600 字，超出按最后激活从旧到新截断。生成时刻与来源窗口写在首行。它每次微代谢写入后重建，每趟 phase B 收尾再重建一次。会话启动 hook 在身份层之后追加这份摘要；文件缺失、为空或不可读时静默跳过，输出与改前逐字节一致。窗口外的条目滑出注入，条目本身仍按衰减走生命周期。

#### 5.6.1 为什么两池白天不注入

1. **两池是还在路上的假设。** 情景池的成功判据是被证伪或被反复证实，语义池的成功判据是毕业。把候选当常量注入，任何一条错判都会在每次会话里被强化。
2. **退注入之后，语义池的存在理由押在「代谢期被读取」上。** 它必须在夜间被真正读一遍，否则既不被读也不被注入，等于悬空。
3. **当场判断缺信息。** 隔一夜再判，能拿到的后续信息多得多。
4. **单一入口避免双写。** 白天写、夜里也写，同一段内容会被两条路径各写一遍，去重成本高于收益。
5. **原始源完整。** 转写由宿主自动落盘，不会漏；让它过夜，代谢时读的是全量，而不是白天挑剩下的。
6. **回边闭环。** 毕业产出的身份层随启动注入，skill 随调用执行，工作环起草计划时读池内判断——同一条记忆服务三种用途：约束怎么做人、怎么做活、怎么派活与预判风险。没有这条回边，代谢只是一份档案。

**身份层预算。** 身份层合计不超过 6,500 字（人格 2,500 + 用户档案 4,000）。超预算的唯一处置是下沉：内容搬进该区的子文件，索引留指针。截断会丢判据，压缩措辞会让规则变形，下沉只多一跳。纠偏摘要追加在身份层之后，不计入这份预算，它自己有 1,600 字的上限。

### 5.7 分流问句

一条信息该进哪边，按以下问题依次判：

1. 是否改变了工作对象的当前状态？命中 → 工作固化。
2. 是否改变了预测？命中 → schema 代谢。
3. 能否写成「不这样做的对照人」？画不出 → 不构成 schema，只做工作事实。
4. 是不是「谁是谁」？是 → 不进池，写人员登记表。
5. 是不是一条非中性的校准信号？是 → 白天就可以落情景池。
6. 是否只对某个具体的人在某类活上的表现成立？是 → 进观测记录，不进身份层，不写 skill。
7. 是否已命中身份层？命中且校准中性或正向 → 不提取。

**两者同时命中时的双编码规则：**

1. 工作结论先固化，schema 随后。不能因为 schema 不达标而丢掉工作事实，这也是 phase A 与 phase B 分段隔离的原因。
2. schema 只存抽象模式与证据指针，项目结论仍以项目权威源为准。
3. 项目文件可以成为 schema 的证据，私区记忆池不存项目结论的副本。
4. schema 被击穿不会自动改写项目历史；项目新事实走工作记忆的更新链。
5. 指针双向：工作侧在当日段写关联指针，schema 侧在来源指针里写转写日期与出处。
6. 节点闭合时把素材逐项归堆：事件类进工作线，schema 类进记忆线，两清单条数之和必须等于素材条数，不留未归类项。两条线由同一次闭合同时展开。

### 5.8 事务、锁与收据

夜链是一条有副作用的长链，中途崩在半路会留下半写状态。系统用事务锁、分段收据和提交闸把它变成可恢复的。

#### 5.8.1 九步不变量

顺序本身就是正确性：

1. 机械解析唯一的目标逻辑日与版本化窗口，确认已闭合。禁止模型自己算日期加减。
2. 抽取前占按逻辑日唯一的互斥锁；已有有效提交收据则幂等退出。
3. 生成不可变的转写包；phase A 与 phase B 各自全量读完全部分片，各自留覆盖收据。
4. phase A 先完成工作层固化，留绑定运行标识与覆盖哈希的收据；phase B 再做两轴裁决，留独立的判决收据。
5. 提交前跑本端记忆审计；平日跳过周段专属的衰减闸，周日必须包含该闸。
6. 账本落账成功、且 UTF-8 解码与替换字符检查通过之后才可提交；提交绑定覆盖、判决、phase A 与池文件哈希。
7. 目标日早于探针时走追溯提交：闭合旧账，不回退探针，并使受影响的后续后态收据失效待复核。
8. 提交后释放锁并留正向解锁收据；出口必须校验为绿。已提交但缺解锁收据时，允许机械回收垃圾锁；未提交的外来锁仍须人工确认。
9. 任一硬闸失败即停在当前阶段；已完成的工作层产物不因后续失败回滚；探针不得提前推进。

#### 5.8.2 锁

锁文件放在产物目录之外的 `_locks/`。两个实测理由：抽取器的取代逻辑会把转写包目录下除归档子目录外的全部内容搬走，活锁会被连带搬走，互斥当场失效；占锁先于抽转写，锁若落在转写包目录里，抽取器会看见一个「有内容无清单」的目录并向用户索要强制参数。

**持有者身份由环境推出，不经模型复述**：排程运行标识优先，其次会话标识；两者都缺则拒绝占锁。

**四种状态：**

| 状态 | 处置 |
|---|---|
| 已获取 | 继续 |
| 被接管 | 原持有方的会话转写（含子代理转写）最近一次写入距今超过 2 小时，由锁闸自动接管；授权、原持有方、闲置时长与转写证据写进锁的接管块，随解锁与提交两份收据留痕 |
| 被占用 | 立即停手报处置建议，不抢占 |
| 人工抢占 | 须同时带用户的授权声明；缺声明仍按被占用处理 |

**判活的唯一证据是持有方的会话转写。** 进程号记的是已经退出的锁子进程，心跳只在占锁时写一次、没有刷新循环，两者都不具备存活区分力。找不到转写就无从判闲置，按存活处理。闲置时长从「转写最近写入」与「占锁时刻」两者中较晚的那个起算，所以刚占的锁在 2 小时内一定接不走。

**临界区守卫**：读旧锁、判闲置、覆写这三步包在文件锁里，否则两个执行体会同时判到闲置。

**围栏**：四个事务写入（写 phase A 收据、登记判决、提交、追溯提交）每次写入前比对锁上的身份与本进程环境，不符即拒。接管之后，原持有方即便醒来也写不进任何收据。不经锁闸的写入（工作库落位、节点段、两池落盘、周段、账本与待裁项）在开写前、以及任何中断续跑之后，先核对持锁，不是持有方就停手、不写、不解锁。

#### 5.8.3 提交闸

提交前逐项核：覆盖收据通过且运行标识等于当前；本运行体仍持锁；判决收据存在并通过同一校验器（含基线哈希、行与候选一一对应、候选证据未被改写）；phase A 收据通过（有覆盖就必有覆盖收据）；全部落盘文件严格解码无替换字符并记哈希；账本含目标日与运行标识；记忆审计固定脚本退出码为 0。

**探针单调**：目标日早于探针须改走追溯提交；跳过中间日时排程不得自行认缺，须逐日补，或交互式逐项确认并把缺口清单写进收据。追溯提交另需先持久化「作废待办与完整下游作废计划」，逐项作废完才转提交，中途失败按计划幂等续跑。

**三段式写入**（先记 PREPARED → 再推探针 → 再记 COMMITTED）让每种崩点都留可判别的痕迹：无收据且探针未动，是干净中止；PREPARED 且探针未动，可续跑；PREPARED 且探针已动，是假绿窗口；COMMITTED 且探针未动，可回填。判定词表覆盖二十种左右的非绿态（覆盖未过、旧运行、收据漂移、判决缺失、审计未绑定、解锁未证、后态已被更早补账作废等），全部不判绿。

#### 5.8.4 收据、续跑与账款

- **完成只认提交回执**：本链完成只以提交命令写出、校验通过的收据为准，不另写任何完成回执或自造标记。曾经有一趟把转写整理成十八份笔记当完成收工，又三次自写完成标记应付续跑提示，中间六步一步未做。
- **续跑**：收到续跑提示先核对持锁，再按段收据找出第一个缺失的段，从该步续跑；段收据都不在时，从抽转写之后续跑，已落盘的分片不重读。
- **账本**每条必含：phase A 固化摘要（含覆盖数）、容量四池原始读数、两轴分流结果、巡检 FAIL 与 WARN 计数、待裁声明（须用户确认的 C 项一行，主 agent 已按常设授权裁决的逐项另起行）。周日追加周复盘条目，只记记忆系统自身的代谢，含衰减前后两组实测数。
- **夜跑提交回执**在解锁之后写进推送目录，过校验后落盘并在通信区追加一条同键回执。状态三值：四件齐备记已提交；提交过了但审计红、解锁收据缺失或周段中断记部分完成；提交未成记失败。这份回执是记忆操作披露的载体，随晨间推送转述。
- **存储执行器**：两本账的读写一律交固定的书记 sub-agent；唯一例外是落账连撞三次限流，此时主 agent 破例直写，硬约束是只走原生 UTF-8 编辑、写后验替换字符为 0、并在条目内标注兜底直写。

#### 5.8.5 补跑

- **触发**：当日首个会话发现昨夜事务未闭合（转写包或收据缺失、覆盖或判决未通过；「已提交但漂移」不算断档），或周一发现上周归档件缺「本周产出」节，后台派补跑 agent。
- **规则**：一次一个逻辑日，日期由派单方显式给出，不自算、不推断、不扫描「还缺哪些天」；锁的持有者用补跑专用前缀，便于收据辨认；目标日早于探针走追溯提交；不重复派（判据是转写包内有无失败记录或账上有补跑标记，不靠「我记得派过」）；多日缺档逐日派，一次一天。
- **派单护栏**：只准派书记 sub-agent，深度上限 2；禁派自己、禁工作流工具；单次并行不超过 4，整趟累计不超过 20；禁碰排程。根源是历史上一次 sub-agent 递归扇出近 200 个下级、单轮成本失控的事件——「自己找活干」是扇出失控的起点，所以「单目标日」与「禁止自扫缺口」和扇出上限同等重要。
- **失败必须落文件**：成功时账本与提交回执就是地面证据；失败或中途停手写一份补跑尝试记录（持有者、逻辑日、尝试时刻、停在第几步、原因、处置建议）。
- **与主对话的写入冲突**：目标日流水段写的是过去日，不冲突；全局状态与项目主文档可能撞——派书记写入前先读回，按幂等键替换，发现该键内容在读取后已被改动就停手报冲突，不覆盖。

### 5.9 周段、季度与月节点的位置

- **周段**（目标逻辑日为周日）：核对前置 → 写「本周产出」 → 归档当周工作台 → 更新长期记忆 → 校准全局状态 → 建新一周工作台并写周一日段 → 周级池代谢。周级池代谢是跨情景情景池升语义池的唯一门，也是时间衰减的唯一执行者。
- **季度归档**两模式：检测模式由周段自动调用，只判定季度点、清点三区待归档条数与体积，到点时在待裁项里写一行，零归档写入；执行模式须授权，按三区顺序搬运（先落归档件、确认字节数不小于移出段才动源文件），顺序不可换，中途崩才不会永久丢段。检测绝不能自行升格执行。
- **月节点**：排在周段返回之后，读刚闭合的周结果；月节点的任何状态都不阻塞最终提交，它的账记在提交回执与工作台里，不进记忆账本。

## 6 · loop 系统 Chronos

Chronos 管环什么时候转。

它的对象是一条从终点目标一直拆到今天的链路：终点 → 月 → 周 → 日 → 日内的动作条目。每一步都写下预期，完成时回来对账，偏差带原因，改完出下一步的计划。一天里的顺序是：清晨收到今天要做什么，白天按条目执行，夜里把刚闭合的那一天拆开、对账、起草明天，次晨送达。

Chronos 只负责「什么时候、按什么规则转、产物落在哪」。转出来的事实怎么沉淀往哪里写，归代谢系统（§5）。

### 6.1 逻辑日

一天不是自然日。系统里的「今天」叫逻辑日，窗口固定为 `[D 04:00, D+1 04:00)`，D 是日期。

- **日界线设在凌晨**，不在 00:00。夜里的连续会话在物理上跨了午夜，按 00:00 切会把一段连续工作劈成两个逻辑日，两边都不完整。界线要落在用户实际作息的分界处，初始化时按用户的作息答案确定，之后固定。
- **会话转写按时间戳落进窗口**，夜链只读属于目标日的那一个窗口。
- **排程字段按物理钟填**，逻辑日写进任务提示词正文。两套时基不能混用。
- **目标日 D** 是夜链正在处理的那个已闭合逻辑日；**推送日 P = D + 1**，是计划要送达的那一天。
- **目标日、星期几、次日日期全部取自机械件的读数**，模型不自算日期加减。日期算错一位不会报错，会把一整天的工作记到错误的日子上。

### 6.2 目标树

目标树有四层，另有一个日内的动作层。

| 层 | 载体 | 结构 |
|---|---|---|
| 终点（长期） | `_goals.md §目标树` | 每个环一组：指标、口径与处置、节点（终点值加逐月节点）。终点是整棵树的时间锚点 |
| 月 | `_goals.md §当月` | 周期、复盘日、状态行、周划分；每个环一块：本轮目标、按周排列的动作（缺来源写「无节点来源」）、预期、实际结果、偏差和处置 |
| 周 | `_current.md §本周目标` | 总表（十列，见下）+ 日拆解 |
| 日 | 日拆解的一行 | 日期、星期、当日目标 |
| 日内 | `_current.md §进展记录` 的日段 | 环内条目（五字段，见 §6.2.4） |

`_goals.md` 的 frontmatter 记着环起算日。目标日早于环起算日时，日节点与周节点一律记 SKIPPED，读作「工作环还没开始」，不是失败。月度复盘的回顾范围按周归属：周一落在哪个月，整周归哪个月。

**没有独立的季度目标层。** 季度只作为归档目录存在（§5.6）。

#### 6.2.1 工作台的区块顺序

`_current.md` 是一个「周切片」：每周一份，周日归档，换新文件。

区块固定顺序：frontmatter（周次与起止日期）→ 加载链 → **本周目标** → 任务清单 → 原始口述 → **进展记录** → 本周产出（归档时补）。

「本周目标」内部依次是：

1. 本周目标总表；
2. 日拆解；
3. 收口日行；
4. 进度行；
5. 两个周级子块：「周复盘初稿」（周五目标日那趟夜链写）、「下周安排」（草稿与定稿）；
6. 审定记录行。

这些块都不属于任何日段。日段只出现在「进展记录」里。

#### 6.2.2 本周目标总表

十列：编号 / 短名 / 目标 / 负责人 / 上级 / 截止 / 环 / 状态 / 原因 / 还要做什么。

- **是否在位只认机械件读数**，不凭目视。总表缺位的周退回兼容口径：本周几项 + 周看板 + 按日分配。
- **编号**：用户本人的周目标用数字，团队目标加 `T` 前缀，按负责人排。
- **短名**不超过 12 字；推送正文写事情名称取这一列。
- **上级**：团队行指向它服务的用户本人编号；用户本人的行留空。
- **状态六值**：完成 / 进行中 / 有风险 / 卡住 / 未开始 / 搁置。
  - 「有风险」由夜里按可达性判定写入，原因列附依据。
  - 「搁置」只凭用户原话写入。搁置行不进入次日计划、不结转、不进收口单、不计逾期、不判风险，但行留在表里，由下周拆解照常结转。
- **行键**三种写法：总表编号列原值；条目与进度行里写 `#<编号>`；审定流写 `row:<ISO 周>#<编号>`。裸编号不是合法键。
- **日拆解**：当日目标一项一句，「编号 + 一句」，多项用「；」分隔。**格里编号的先后就是那一项动作在当天的优先级**，排前的先做。
- **收口日行**：`收口日：<MM-DD> 周X`，写明这一周哪一天收口全部工作，缺省周五。格式不合、日期不在该周、周几与日期不符、同周多行，一律按周五读，并在读数里给原因。
- **进度行**：`进度 · <时间戳> · #<编号> <状态>：<一句>（<来源>）`。白天追加在日拆解表（和收口日行）之后，谁执行谁追加。

#### 6.2.3 日段

日段标题是一个字面量：`**<日期> 周X · 环内计划（<起草者>起草）**`。审计器、推送装配、周级做梦、夜链都按这个字面量机械识别，改格式等于让这些环节看不见这一段。同一个逻辑日可以有多段。

#### 6.2.4 环内条目

每条五个字段：

```text
*条目 N — [环] 简短标题 · 执行：<成员>*
- 本轮目标：<环名>；上级：#<总表编号> | 周看板块 | 本周目标 | R-<id>
- 动作：……
- 预期：做到什么、哪天、谁做、依赖谁或等什么
- 实际结果：待填（夜里填）
- 偏差和处置：待填（夜里填：差距、原因类、下一步）
```

- **编号**在日段内从 1 起，按列出的顺序编。跨日引用写成 `日期#N`。审定新增的条目接续编号；删掉的编号不复用。
- **上级**写在「本轮目标」里。上级不是总表编号的条目（总表缺位，或是递归执行条目），闭合时不追加进度行。
- **执行者**写在标题行末。没标时机械件记为用户本人并标 `executor_declared=false`，推送里记「未标」。被标成其他成员的条目，事实只写进执行流水，由夜里回填。
- **顺延自**：结转条目的动作首句写 `顺延自 <原编号>。`。没有这句话，顺延链就断了，后续的对账与统计都会失真。
- **上限**：每个日段不超过 12 条（含执行条目），单条不超过 300 字。环内计划段不受 600 字的段级约束，非环的流水段才受。
- **越界**：提交号、语义化版本号、测试数或文件计数、代码与配置片段、推论链，都不得写进进展记录，应当下沉到项目文档。提交号只存在于执行流水和代码仓库。
- **预期怎么取**：总表在位时取该行「目标」「截止」「还要做什么」；预期栏是占位值（「预期待补」之类）时，改取「动作」里的「验收：」子句；都取不到就记「缺预期」。
- **每条写产出**：一条条目要写出它对上级目标的产出（做出什么、给谁用、哪天）。发消息、约时间、要材料属于「动作」里的步骤，不单独成条。需要思考的事写成思考产出，例如「框架 v0 与问题清单」。

#### 6.2.5 标签

环标签 `L1`–`L4` 标识的是目标环（个人 / AI 贯穿 / 团队 / 客户），与角色无关。

指标标签写在行内，形如 `@lx.key:value`，只数标签，不从上下文推断。机制固定的是标签的写法和写入方，每个环具体写哪几个 key 属于配置。

| 标签 | 谁写、何时写 |
|---|---|
| `@l1.commit:open` | 夜链 phase A：目标日会话里，用户以「可交付」口径给出的承诺型判断。行内带五要素：验收人、使用标准、日期、把握、问题定义；缺项写「待补」，不补写 |
| `@l1.commit:hit` / `:miss` | 日节点：承诺的日期不晚于目标日、且没有检验行回指时，按证据判 |
| `@l3.exam:pass` / `:fail` | 日节点：目标日的实际结果里记录了评分结论时 |
| `@l4.due:<短名>:<日期>` | 日节点：总表 L4 行的截止是日期 |
| `@l4.accept:ontime` / `:late` | 日节点：到期日及以前验收记 ontime；到期日已过仍未验收，到期次夜记 late，不重写 |
| `@l4.delay_found:<短名>:<日期>` | 日节点：带截止日期的项目在到期前首次被判卡住或有风险 |
| 用户手写的标签 | 用户回复一句话后，收到回复的会话把标签行单行追加进当日日段，夜跑原样保留 |

通则：证据不足不写；已有同名同日期的标签不重写。承诺检验在证据不足时写「证据不足，次日再判」，不打标签。没把握的探索性判断写成待验证判断，不打标签，也不计入命中率分母。

### 6.3 夜链：一夜走完四相

夜链是 PGL 的主动作，由宿主的唯一一条每日定时任务触发，一次处理一个目标日。整条链按固定步序执行，每一步都有自己的收据。

**分段与降级。** 链分三段：工作固化的 phase A、目标环节点段、记忆代谢的 phase B。三段隔离：

- 任何一段的任何缺口都不阻塞 phase B；
- phase B 失败不回溯影响节点段已经写出的回执；
- phase A 与 phase B 是两笔事务，phase B 失败不回滚 phase A。

| 步 | 段 | 做什么 |
|---|---|---|
| 1 | 前段 | 定目标日、占事务锁、抽转写 |
| 2 | phase A | 幂等判定 |
| 3 | phase A | 回放转写、收通信区增量 |
| 4 | phase A | 落位工作库 |
| 节点 | 节点段 | 日节点、周节点、推送包装配 |
| 5 | phase B | 容量扫描 |
| 6 | phase B | 分片回放 |
| 7 | phase B | 两轴判定与日级代谢 |
| 8 | 转调 | 周日转调周级做梦；月节点条件满足再转调月节点；补装推送月层 |
| 9 | 收尾 | 巡检、落账、提交事务、释放锁、写提交回执 |

**第 1 步 · 定目标日、占锁、抽转写。**

- 目标日的选法：默认取最新闭合的逻辑日；上一夜失败时续跑最早未闭合的那一日，后面的日子不得越过它。禁止模型自算日期。
- 占事务锁（§4.8）。
- 抽转写只抽取以用户原话为锚的三段，分片落盘，不把整天的原始转写塞进主上下文。
- 目标日没有任何会话、且窗口已闭合时，走「零会话日闭合路径」：链照常闭合，节点段与推送装配照常运行，只是没有可固化的会话事实。

**第 2 到 4 步 · phase A 工作固化。** 细节见 §5.3。

**节点段。** 每晚运行，先于 phase B，因为推送包要读当夜的对账结果，而代谢只改判断倾向，不影响当天的事实。

- 日节点：每个目标日都跑，无会话也到期。
- 周节点：目标日是周日才跑，跑在日节点之后、推送装配之前。
- 推送包装配：每晚都跑，读目标日 D 与推送日 P。
- 月节点：在 phase B 之后的第 8 步才转调，因为它要读刚闭合的周结果（§6.4.4）。

**第 5 到 7 步 · phase B 记忆代谢。** 细节见 §5.4 到 §5.7。phase B 的事实层输入取当夜的日节点回执，另加白天纠偏行作第二来源；日节点回执缺失时记零并留痕，不阻断。

**第 8 步 · 转调。** 判断「周日」用的是目标日，不是今天。先写周段入口收据，记下 phase A、节点段、推送装配、phase B 四项收据是否在位，再调周级做梦。月节点的前置条件是四项收据齐备且月界判定为真，任一不成立就写 BLOCKED，不调用月节点。月节点返回后再调一次推送装配，补装月层。

**第 9 步 · 收尾。** 跑巡检 → 落账 → 提交事务 → 释放锁 → 写提交回执。**完成只认提交回执**：只有这一步写出的回执，且经校验通过，才算这一天闭合；不另写完成标记，也不自造。

### 6.4 节点

#### 6.4.1 日节点

日节点是环的核心，每晚对刚闭合的那一天做六件事。

**一、前置判定与审定合并。**

- 状态判定：GO；SKIPPED（目标日早于环起算日，唯一合法来源）；ALREADY_DONE（当日已闭合，幂等跳过）；REJECT（缺参或非法，零写入）。
- 缺计划：目标日没有日段，或日段里没有环内条目，且不是空白日时，仍走 GO，记一条流程偏差「缺计划」，后续的到期、可达性、到期检验照判。
- 审定合并：读两端的审定流，按条目键分组，逐条把用户原话写回目标日的日段（§4.7）。合并完成才往下走，合并失败按中断处理。
- 空白日判定在合并之后：用户端当日会话数为零、两端执行流水任务行为零、两端审定流行数为零，三项同时成立才是空白日。空白日不记缺计划，也不记任何流程偏差。

**二、取数。** 四类来源：会话转写、当日触碰的文件、外部镜像的差异、执行流水与代码提交。外部镜像只读盘，拉取归对等端；镜像登录过期只记缺口，由用户本人重登，系统不执行登录命令、不读凭据。

每类来源缺数据时写一行缺口后继续，用本地证据往下走。缺口有固定词表（认证过期、拉取失败、窗口内无拉取、差异缺失、无运行目录、无最新快照、无当日回执、无周文件、周已归档、无执行流水、流水格式非法、通信区流缺失、仓库读取错误、审定流非法），写缺口是为了让降级可见，不是为了阻塞。

**三、收集实际结果。** 按条目与项目锚点检索转写、触碰文件、镜像差异、执行流水。总表在位时另取第五类证据：总表行证据，取证范围包含日拆解点名的行、条目上级引用的行、窗口内的进度行、对等端在通信区发的同格式进度行、以及审定流里以行键点名的行。

检索面覆盖条目创建以来的各日；顺延条目沿「顺延自」链回溯到最早一条。证据指针有六种形态：逻辑路径、镜像差异路径与键、转写锚点、日回执路径与键、执行流水路径与行号、通信区稳定键。

**四、逐条对账。** 每条在「实际结果」里写事实、证据指针和完成状态（完成 / 部分完成 / 未完成 / 阻塞 / 无证据），对照预期判差距。状态不是完成、或完成日期晚于预期日期的，在「偏差和处置」里写差距、原因类和一个假说。

**原因类四选一**：计划（预期本身排错）/ 执行（没跟上）/ 外部（在等客户或他人）/ 目标变动（用户或上游改了目标）。

对账有两条硬规则：

- **判未完成要有正面证据**。检索面里能看到「没做完」的事实，且该记录晚于条目写成的时间，才算。更早的「未发」「未交」类记录可能已经过期。完成与未完成都找不到证据的，状态记「无证据」：不判偏差、不写原因类、不计入完成数，条目照常顺延，次日草稿在动作末句带「前提待核：<问题一句>」。
- **缺预期不计偏差**。预期为空的条目记一条流程偏差「缺预期」，不进按期完成率，也不向用户追问，只在前夜简报里合并成一行。

带执行者的条目，证据分三档：① 该端执行流水里指向本条的任务记录（主证据）；② 没有流水时取通信区里点名该项目的帖子，与未点名的仓库提交、当日触碰文件、转写交叉核对；③ 都没有时写「无执行流水」，状态记无证据，另记一条流程偏差。执行流水已经收口（有收口行）而仍没有本条记录的，实际结果写「未执行」，按预期计偏差。

**总表回写**按证据改三格：

- 状态：改状态须有正面证据。目标已做到记完成，已开工未做到记进行中，被外部事项挡住记卡住；用户原话把事搁置、暂停或定为等他人消息的，记搁置，优先于卡住。回写不把状态改回未开始；完成或搁置的行只在用户原话改判时回写。
- 原因与下一步：有新证据时各写一句；没有新证据时状态不动，原因末尾加一个「（某月某日 无新证据）」括注，下一步不改。
- 编号、短名、上级、环四格夜里不改；目标、负责人、截止三格只按用户原话改，并在原因末尾注明「按用户某日某时原话改」。原话新增了本周要做的事而表里没有对应行的，在表末加一行；同一件事已有行的改那一行。不删行。

**五、迭代与递归。** 当夜的固定顺序：裁决（主 agent 裁决类提议）→ 失效判定 → 生成执行条目 → 到期检验 → 登记新提议。当夜新登记的提议不参与当夜的裁决与失效判定。

- **到期项**：回读全部未结承诺，日期不晚于目标日的按证据判命中或未中，在当日日段末尾写检验行。判未中的当夜登记提议。到期未兑现的其他环承诺只记偏差，由下一个节点登记提议。
- **周目标可达性**：对总表里状态不是完成、也不是搁置的行，按「到截止的剩余天数 × 本周实际速度 < 剩余量」判。不可达就登记提议，前夜简报写一行风险，同时把该行状态改「有风险」并写明依据。可达性判定只标记，不改目标、不改阈值。
- **机制递归、失效、到期检验与执行条目**见 §4.6。
- **现状核对**（除周日外的每个目标日，次日草稿之前）：对次日每一条条目（夜跑起草的与会话里提前写好的）核对四件事：是否已完成或已不需要；信息类条目能否先自答，答不出就在动作末句写「已查：来源；缺：什么」；口径与状态值是否与用户最新审定、正典现行取值一致；前提依赖用户本人动作而所据记录早于次日前一日的，标「状态待确认」并附原文，不据此写成待做条目。夜跑起草的条目按核对结果直接删改；会话里提前写好的条目一条不改，只在段末追加一行前提核验。
- **次日草稿**见 §6.4.2。

**六、产出与回读验证。** 汇总后的正文经写入管道落盘，再写回执。回执先过形状闸（条数上限、字段形状、偏差与计数的一致性），形状不合格拒写，原回执一字节不动；写入用原子替换并回读核对时间戳。状态分五种：DONE（加载链审计通过）、GAP（有缺口但落盘完整）、SKIPPED（目标日早于环起算日）、INTERRUPTED（落盘失败，带停点，从停点续跑）、REJECT。

**前夜简报**不超过 8 行：先写结果与影响，再逐项写待裁。内部字段名、哈希、阶段名只进末尾的核验依据，不写进简报正文。简报进推送包的夜间备注，不进推送正文。

#### 6.4.2 次日草稿：按收口日选模板

次日草稿的形态由「次日是星期几」和「收口日是哪天」共同决定，按顺序核，命中即止。

以收口日缺省为周五为例：

| 目标日 → 次日 | 模板 | 内容 |
|---|---|---|
| 周一至周三 → 周二至周四 | 常规 | 总表在位时，日拆解次日那行的每个编号出一条，加上目标日未完成的条目结转（上级是搁置行的不结转）；总表缺位时按日分配的次日那一行、周看板的下一步、结转 |
| 周四 → 周五 | 收口单 | 总表里状态不是完成也不是搁置、截止不晚于收口日的每一行出一条，标题带「收口」，预期写「今天收：……」或「收不了：原因；转……」 |
| 周五 → 周六 | 遗漏与异常 | 收口单没收下的行、本周阻塞与外部等待的事项、本周流程偏差各一条，另加一条「周复盘初稿与下周草稿：看过并标出纠偏点」 |
| 周六 → 周日 | 复盘日 | 与用户过复盘、定下周安排、发周报各一条，加周六未完成的结转 |
| 周日 → 周一 | 不起草 | 周一条目由推送装配的周一分支与周级做梦承接 |

排序规则：

- **条目的次序就是当天的优先级**，草稿与推送保持这个次序，不按编号、负责人或环重排。
- 逾期结转（上级所指总表行的截止已经早于次日）排在前面，截止早的在前；其余结转排在日拆解条目之后。
- 目标日条目与次日日拆解点到同一编号时，并进那个位置，位置不变，动作首句写「顺延自」。
- 一格里并列多个编号的写成一条，位置取并列中的第一个。
- 超过 12 条时，只合并结转与收口单里未被点名的行；日拆解条目和递归执行条目单列，不合并。
- 空白日的条目整体并入次日模板，预期原文照带，编号重编，首句写「顺延自」。

周五目标日那趟夜链另写两个周级子块，落在「本周目标」末尾：**周复盘初稿**（范围周一至周五，含逐环实际结果、按期完成率、偏差按原因类分布、流程偏差、复盘基准，末尾单列至少三个纠偏点，每点一句、每行不超过 40 字）与**下周安排草稿**（总表在位时为下周总表加日拆解）。两子块已存在时不覆盖。周日与用户过完复盘后，草稿标题改为「定稿」。

#### 6.4.3 周节点

周节点在目标日为周日时运行，是日节点的加长版，做的事有五件：

1. **周复盘条目**：逐日读七日日段与日回执，按环汇总，追加在目标周「进展记录」末尾。内容含四个环各一行「本周实际结果；周偏差」、一行环流程偏差汇总（缺计划日数、缺预期条数、缺日回执日数、缺执行流水条数、空白日天数）、一行按期完成率与原因类分布、一行所用复盘基准、一行关联指针。周复盘只引用日段结果，不新写标签。
2. **复盘基准**四级，依序取：当周的用户审定行 → 周看板的「完成定义（已定）」→ 本周目标状态行所引的验收裁定 → 原计划。总表在位时，总表行的「目标」作完成定义、周日夜回写后的「状态」作结果，替代后两级。
3. **月目标可达性与计划校准**（§4.6）。
4. **下周拆解**：只写进暂存区，不直接写工作区。来源依序取：周日定稿 → 下周安排草稿（按周日后的进展修订，差异写进简报）→ 月节对应周行加本周未完成结转。来源缺失的格写「无节点来源」，不脑补。新总表的编号重排，上级随编号同步改写，状态沿用周日夜回写后的值，原因写「结转自本周 #<旧编号>」。
5. **周档切换**（由周级做梦执行，§5.6）：周复盘条目写完 → 补写「本周产出」→ 把 `_current.md` 改名移进按年季分的归档目录 → 建新的 `_current.md`，并把下周拆解写进「本周目标」→ 未完成任务作「继承」项滚入新周 → 写长期记忆的本周节。

新周文件建好后紧接着写周一日段。条目来源依序取：周一推送包的条目 → 下周拆解的周一行加周日未完成条目 → 只写一行「周节点未产出拆解，周一无计划」。

#### 6.4.4 月节点

月节点的触发条件是：目标日是周日，且下周一的所属月不同于本周一的所属月。它排在周级做梦返回之后，因为它要读刚闭合的周结果。

月节点做七件事：

1. **前置校验**：周段入口收据在位、周段状态为 DONE 或 GAP、周段闭合、长期记忆里有回顾周所在节的周节；任一不成立就不调用，写 BLOCKED。
2. **回顾范围**：周一落在回顾月内的各周。上月没有月复盘时，把周一在上月、周日在回顾月的那一周并入。
3. **月目标对账**：逐环逐条判达成 / 部分 / 未达 / 无证据，写事实与证据指针；同时产出全月回顾（每个项目一行，列月初状态、月末状态、出现周次、是否在计划外）、跨周趋势（每周一行，回顾周不足两周写「样本不足」）、周对账表、偏差清单、终点可达性判断。终点可达性只做对照，不改目标。
4. **月度指标**：十项，每项写值、样本数、状态（已计算 / 无数据 / 需外部输入）。分母为零记无数据，不插值；首月大面积「需外部输入」属于正常，照实写。
5. **月级递归与阈值校准**：补登日、周节点遗漏的到期项；主线口径核对（把长期记忆里「主线」点名的目标或定义与全月回顾逐项对照，近四周里出现不足两周的点名项登记提议）；到期检验；阈值校准（§6.6.5）。
6. **下月周拆解**：起草下个月节。只拆到周粒度，按天拆解归每周日的周节点。月中未达的结转标「结转自本月」，预期按新月节点的验收口径重写。
7. **月节归档**：把回顾月那一节移进归档件，再写简报（不超过 12 行）。

月节点的简报进推送包的月层。月层在装配当夜先是占位（一行「月复盘装配中」），月节点返回后补装。

### 6.5 推送包

推送包是 PGL 对用户的唯一主投递：一份 JSON 加一段纯文本正文。JSON 供下游读取，正文供人读。

#### 6.5.1 装配

三条路径：

- **夜间装配**：节点段末尾，早于 phase B，读目标日 D 与推送日 P。
- **月层补装**：月节点返回之后，只替换月层与正文的「本月」行，其余字段沿用。
- **会话按需**：用户在会话里问计划时。包在就只读出正文；包缺、但昨夜事务已提交，就从暂存的地面文件恢复参数重新装配；包缺且昨夜未提交，不装配，直接回报「昨夜事务未闭合」。

装配幂等：已有推送包的运行标识与本趟相同就不重装，只核对并补齐通信区回执行；不同则整体重装覆盖。

#### 6.5.2 正文五节

正文写给不看日志的人。五节次序固定，第一节必有，其余无内容时整节省略。第一节标题就是正文第一行，不加抬头和问候。

1. **今天你的优先级**：用户本人当天的事，不超过 5 条，行首用「1. 」到「5. 」。次序取当日条目序，容量裁决产出了排序时改取排序结果。每行写「时间或截止 · 做什么 · 要到什么结果」。超过 5 条时，其余的事归到第三节。
2. **今天交给你的**：当天日拆解里负责人是团队成员的团队行，不超过 5 条，按时间先后，每行写「时间 · 谁 · 交什么」。
3. **本周还差什么**：用户本人的周目标里状态不是完成也不是搁置、且没在第一节写过的，不超过 8 行，每行写「事情 · 截止 · 状态词 · 一句原因或下一步」。状态词按序判：截止早于推送日 → 逾期；总表状态卡住 → 卡住；有风险 → 有风险；截止不是日期 → 待定；其余 → 按期。排序是逾期、卡住、有风险依次在前，其余按截止先后，非日期截止居末。「已完成」与「搁置」各合成一行。
4. **要你定的**：只有人等他决定或给材料时才写，不超过 3 条，每条是一个他能直接回答的问题。来源包括：前提待核项、待审定的周 / 月计划、递归提议（保留两个回复键与「不回则：……」）、待裁项、总表里写明等他确认的事、周一的孤儿清点、周六的周复盘初稿提示。进这一节的每个问题先过「已答核对」（§6.7.3）。
5. **异常**：只写影响本周目标的异常，不超过 2 条，每条一句话，写明影响哪件周目标。空白日时首条写「昨日空白日，计划顺延」。

推送日是周一时，在第三节标题前加至多两行「上周收口」；推送日是每月首个周一时，再加至多两行「本月」。

**硬规则**：

- 每件事全文只出现一次。
- 指推送当天写「今天」，不写星期几。
- 写事情名称取总表短名。
- 编号、版本号、文件名、回执名、夜跑与镜像术语不进正文。
- 不需要用户裁决的内部读数（待裁项总数、审计排期、闸的存量读数）只进夜间备注。

#### 6.5.3 机械核与压缩

正文上限：日层 25 行 600 字；日加周或日加月 35 行 900 字；三层 45 行 1200 字。各节条数上限依次是 5 / 5 / 8 / 3 / 2。

机械核检查：首个非空行是第一节标题；节标题只取那五个（外加周层、月层标签行）且按序；禁用词（编号、带小数点的版本号、文件名与扩展名、一组内部术语、一行内三个及以上并排的裸数字）；递归提议不超过 3 条且每条带「不回则：……」；条目的日期等于推送日且不重复，预期非空。

不过就压缩，压缩次序固定：缩第三节原因句 → 缩「已完成」「搁置」两行 → 缩第二节 → 从末行起删第三节的行（逾期、卡住、有风险与写了当天一步的行最后删）→ 缩第一节材料说明 → 周层月层缩到各一行。第一、四、五节的条目不删。三轮仍不过，正文只留第一节前 5 条（每行只写时间、事情、结果）加一行「本周其余目标见本周目标总表」，再保留原有的「要你定的」一节；仍不过就不落盘。

#### 6.5.4 送达

推送包由投递适配器在清晨投递，正文整段转发，不加抬头、不重组。投递端每个推送日开一个对话，周内续发，用户的回复按审定流转录。包缺时投递端转达「计划未就绪」并附本周各线目标，不轮询、不迟到补推；送达回执写进通信区。

### 6.6 递归

递归是环改自己。它改的不是今天的计划，是「计划怎么定、预期怎么写、对账怎么判」。

#### 6.6.1 五类触发

| 类 | 在哪判 | 条件 |
|---|---|---|
| 到期项未兑现 | 日节点（承诺类当夜判）；其他环到下一个节点 | 承诺到期被判未中 |
| 节点可达性失败 | 日节点判周目标；周节点判月目标；月节点判终点 | 周：到截止的剩余天数 × 本周实际速度 < 剩余量。月：剩余周数 × 本周完成率 < 剩余目标。终点：剩余月数对照节点要求 |
| 阈值校准 | 月节点 | 该项样本数达到下限 |
| 机制递归 | 日节点 | 同一种流程偏差连续 3 个日节点出现 |
| 计划校准 | 周节点 | 本周参与对账的条目合计不少于 5，且「计划」类偏差占本周偏差总数不少于 50% |

**连续晚数**按日回执逐日向前数，缺回执的日子与空白日计作中断。登记表里已有同类机制提议且未结的，不另开新行，只更新连续晚数。

#### 6.6.2 生成者类与裁决

| 类 | 含义 | 裁决者 |
|---|---|---|
| A | 用户的目标与裁定 | 用户 |
| B | 方法与规则（含主 agent 自己的计划） | 主 agent 按常设授权裁决 |
| C | 环本身 | 主 agent 按常设授权裁决 |

阈值校准不论生成者类都交用户裁决；机制类提议全部归主 agent 裁决。

登记当夜，简报写一行拟裁决（拟采纳或拟驳回，附一句理由），并写明「下一夜裁决；要改直接回复采纳或驳回」。主 agent 裁决类提议在下一个日节点的事务内裁决，裁决理由与撤回方式一并写进登记表。用户在这期间已经给出审定的，以用户为准。**夜跑不直接改 skill、正典与目标**：采纳后的改动一律通过执行条目完成。

#### 6.6.3 登记表

每条提议登记一行，列：编号（`R-<YYYYMMDD>-<序号>`）、类型、来源偏差指针、生成者类、提议内容、**预测**、**到期日**、状态、用户裁决、检验结果与证据指针。

- **预测**写「采纳后哪个指标在哪天前如何变化」，标「主 agent 预测」。阈值校准的预测固定写「采纳后下一次月复盘该项判定为保持」，到期日取下月复盘日。
- **状态**：提议 / 采纳 / 驳回 / 到期命中 / 到期未中 / 失效。采纳与驳回只能由用户写；提议、到期命中、到期未中、失效由夜链写；主 agent 裁决类另有「采纳（主 agent）」「驳回（主 agent）」两态。
- **检验结果栏**按时间顺序追加，用分号分隔：裁决、执行条目指针、未执行记录、检验记录、失效依据。

#### 6.6.4 执行条目与到期检验

- **采纳当夜**：在次日草稿里加一条执行条目，写明改动落到哪份文件哪一节、次日完成、谁做、依赖什么；排在其余条目之后，计入 12 条上限。目标日是周日时，执行条目写进下周拆解的周一行。
- **到期检验**：先判执行。沿执行条目及其顺延链读各条的实际结果 —— 已完成，观察期从执行完成日起算，期满按证据判命中或未中；未完成或没有执行条目，记「未执行」，此后每个日节点再判，同一天不重复记。
- **失效**：仍是提议状态、用户裁决栏为空的行，所在周或月已归档、或目标已被用户改写，标失效，不推给用户。

#### 6.6.5 阈值校准

月节点对三类值做校准：

- **终点值**只做可达性对照，按本月实测速度外推到终点，不提调值。
- **节点阈值与机制参数**：该项本月样本数达到下限才判，否则写「样本不足」并给出预计可判定的月份。样本足够时比较实测分布与阈值，偏离就写提案调整（新值、算式、数据行指针），未偏离写「保持」。校准只用本月及以前各月的实测数，不引用外部基准。
- 校准表整表输出，让用户看到每个阈值当前的数据量。

机制参数的初值（随运行校准）：

| 参数 | 初值 |
|---|---|
| 样本下限 | 5 |
| 同因重复 | 成员数不少于 2，且跨不少于 2 周 |
| 周目标不可达判据 | 剩余天数 × 本周实际速度 < 剩余量（保守，只标记，不改目标） |
| 偏差容差 | 完成与否类为 0；日期类为 0 天（偏移不少于 3 天标「显著」）；数量类以预期给的区间为准，无区间为 0 |
| 机制递归阈值 | 同一种流程偏差连续 3 个日节点 |
| 计划校准阈值 | 参与对账的条目不少于 5，且「计划」类偏差占比不少于 50% |

**只提议，不改目标与阈值。** 调整经用户裁决后才写入参数表。

### 6.7 审定流

审定流是用户原话进入工作环的唯一通道。用户在任何场合说的一句判断，都要以逐字原文的形式被记录下来，夜间由日节点合并进计划与对账。

#### 6.7.1 行格式

一天一个文件，每行一条审定：时间戳（ISO 8601，必须带时区）、条目键、类型、原文、来源、转达来源（可选）。

- **只追加**，不改、不删。一句话涉及多个条目时按条目拆行，每行只放与该条目相关的原话片段，逐字截取。原话指向不明时先问一句指哪一项，再记。
- **条目键**五种：条目（`日期#N`）、周（`week:<ISO 周>`，一律指当周）、月（`month:<YYYY-MM>`）、递归行（`R-...`）、总表行（`row:<ISO 周>#<编号>`）。裸编号不是合法键，错误提示直接给出正确写法。
- **无效判定**：不是 JSON 对象、时间戳缺失或格式不对、类型不是审定、转达来源格式不对、来源不是用户、原文为空、条目键不属于五种合法键，一律判无效，不合并，记一条缺口。文件整体读不出来也记一条。
- **转达**：经对等端转达的用户决定，原话、原话时间、来源会话三项齐全才按审定执行，无需回问；缺任一项不转录、不按审定执行。须用户本人确认的事项不因转达而执行。

#### 6.7.2 夜间合并

日节点在状态判定之后、对账之前合并审定，合并按条目键分派：

| 键 | 合并动作 |
|---|---|
| 条目 | 按原话改目标日的日段：预期、内容、删除、新增、改执行标记。预期写原话加转录标记，同一目标日后到的覆盖先到的；原话落不到现有条目时记未合并 |
| 总表行 | 不单独落盘，收进本次证据集；总表缺位或编号不在表记未合并 |
| 周 | 在「本周目标」末尾追加一行审定记录 |
| 月 | 在对应月节末尾追加同格式一行 |
| 递归行 | 登记表对应行写采纳或驳回，用户裁决栏写原话加转录标记；看不出采纳还是驳回的不写，记未合并 |
| 日期早于目标日或晚于目标日 | 不合并，各记一行，原话留在流里 |
| 无效 | 不合并，记缺口 |

合并清单写进暂存区。中断后续跑只合并清单里没有的行，同时间戳同键不重复合并。

#### 6.7.3 问前先查已答

凡是准备问用户的问题（待裁递归提议、现状核对的问题句、周目标风险里的「要不要」、等他给的材料与决定），写进简报之前先查：

- 近 7 个逻辑日两端的审定流；
- 这些日子的会话转写里用户说的话，包括对话进行中插入的话；
- 目标周工作台的审定记录行与进度行。

查到原话就不问，按原话处置，简报记一行「已答：某件事 ← 原话摘句（时间）」。查不到才问。只差一个具体值（人选、日期、数额）的问题，问句里直接写出缺的那个值，不重问已经定下的部分。推送的「要你定的」同口径把关。

### 6.8 白天：执行、闭合与纠偏

#### 6.8.1 节点闭合

计划节点就是日段里的一条环内条目。它闭合时调用闭合流程，一次一条。

1. **定位**：按完成信号回报对得上的条目。恰有一条就继续；多于一条就列候选问用户；一条也没有就停止，回报「不属计划节点，留给次晨夜链」，不写任何文件。
2. **工作线**：结论落项目主文档本体，推导过程落项目的推论链，跨周状态落全局状态，周级推进落长期记忆。
3. **进度行**：在「本周目标」的进度行末尾追加一行。日拆解里点名该编号的各个日格对应的条目全部完成才写「完成」，否则写「进行中」并写明完成的是哪一条。单行追加，追加后回读核对，行在位才算完成。
4. **记忆线**：两个及以上独立事件支撑同一类情境才够格直升情景池；高风险、越权、系统事故、重大安全信号的单次事件可以直升，须写明复审条件。直升天花板是情景池，不碰语义池与身份层。单次信号不动作，留给次晨代谢。

进度行只追加，不改条目的五字段，也不改总表状态格。实际结果与总表状态由夜间的日节点按证据回写。

#### 6.8.2 白天纠偏

用户对当天计划的条次、内容或优先级给出意见——「这条不对」「这条往前」「这条不该今天」——不必等他说「改计划」。主 agent 当场改写当日段，不经夜链、不回确认轮；改动只落在当日段。

改完在当日段末尾追加一行纠偏记录：时刻、原顺序到新顺序（条目编号次序）、依据（用户原话或直接引用）、归因类别（外因 / 阻塞 / 价值 / 目标 / 自驱 / 其他 / 待定）。归因写不出时写「待定」，夜间补，不硬猜。

纠偏是 S 级。它只改当天计划的呈现，不改记忆池，也不改排序规则的长期口径；纠偏要不要升格成规则，由代谢判定。

纠偏行不进推送包的当日条目，但推送的容量裁决会读最近 7 个逻辑日的纠偏行，用作排序输入（§6.8.4）；代谢侧把它当作提取来源之一。

#### 6.8.3 活跃任务表

日段写完即封在当天。一件「日期已定、后果在未来」的事如果只活在日段里，次日推送就看不到它。活跃任务表专门承接这类事。

- **入表判据**（二选一）：文本里出现「明日 / 明天 / 周X / 某月某日前」加一个动作主体；或用户当场交办并给了时间。
- **五列**：任务（不超过 40 字，写做什么，不写背景）、到期（日期或时段，没有日期不进表）、责任、来源（写入它的日段或条目编号）、状态（待办 / 进行中 / 已办 / 搁置）。逾期天数由到期推算，不落列。
- **写入**：夜链 phase A 落位时提取并入；白天用户交办带时间的任务时，主 agent 单行追加。
- **消费**：容量裁决取「到期不晚于推送日次日、状态不是已办或搁置」的条目进候选池。
- **逾期处置**：逾期满 3 天自动置搁置并写原因，不再复制进当天计划，但留在表里。
- **去重**：按任务文本比对，同名合并来源，不新增行。

#### 6.8.4 日计划优先级裁决

推送正文第一节的次序由容量裁决产出。它在当日条目取齐之后、写正文之前运行。

- **容量**取当日可用的时段：从次日日段已占用的时段反推，或用户在会话里直接给出。取不到就视为不设容量约束，全部条目参与排序。
- **五条判据**，按序比较，命中靠前者排前：

| 档 | 判据 | 含义 |
|---|---|---|
| 1 | 外部时点 | 第三方给定的日期或时段：会议、客户调研、等对方回来后的动作 |
| 2 | 阻塞他人 | 这件事放开后，能解除他人或对等端 agent 的下一步 |
| 3 | 价值与验收 | 直接影响收入、签约、客户验收或月节点指标 |
| 4 | 目标到期 | 上级总表行截止已过或本周内到期，或该行状态为有风险 / 卡住 |
| 5 | 自驱推进 | 无人催、有长期复利的事 |

- **排序**：先按判据分档，同档内按条目序。只对进排序的条目标优先级，标号从 1 起连续，条数不超过容量装得下的条数。条目本身的次序不变，排序只体现在优先级与排序结果上。
- **保底**：第 5 档至少保留一条，排在末位。
- **纠偏**：某条候选条目与最近 7 个逻辑日里某条纠偏行的归类、触发情境相同时，按纠偏后所在档位排。一行纠偏只改它记的条目，不外推。
- **没进排序的条目**逐条写明落在哪条判据上；属于用户本人的事按各自周目标行挪进第三节，不静默丢弃。

### 6.9 会话续接与自检

- **续接按需调用**：用户说「继续」「现在什么进度」或点名项目要汇报时运行。日常启动的轻检查不在这里。
- **首会话判定**按记录内的时间戳筛出今天逻辑窗口里的会话，排除本次会话与排程跑。脚本报错时按首会话路径走——宁可多查一次，不漏断档。
- **首会话做三件事**：核对昨夜事务是否闭合；发现断档就后台派补跑 agent 逐日补；读覆盖收据、跑记忆与探针审计，脚本读数与自报不一致时以脚本为准，并点名「日志报 X、实测 Y」。
- **会话自检**：每次会话启动只判两件事——昨夜事务闭合、今日提交回执在位。正常时零输出；异常时每项一行、以告警符开头，脚本恒返回 0，不让会话因检查中断。

### 6.10 失败与恢复

**合法终态与非法终态：**

| 对象 | 合法 | 需处置 |
|---|---|---|
| 日节点 / 周节点 | DONE（加载链审计通过）、GAP（有缺口但落盘完整）、SKIPPED（仅目标日早于环起算日） | INTERRUPTED（落盘失败，带停点，从停点续跑）、REJECT；环起算日之后出现 SKIPPED 读作半闭合 |
| 月节点 | DONE、GAP、SKIPPED | INTERRUPTED、REJECT、BLOCKED（前置项缺失） |
| 推送装配 | 推送包状态 DONE；主线回执已追加或已存在 | 失败并写明原因 |
| 提交回执 | COMMITTED | PARTIAL（提交成功但审计失败、解锁收据缺失或周段中断）、FAILED（非 COMMITTED，备注写停点） |

**缺包与断档**：

- 投递侧缺包：转达「计划未就绪」加本周各线目标，不轮询，不迟到补推。
- 主端缺包：会话按需路径按上面三种分支处理。
- 推送装配失败不阻塞 phase B，原因进最终汇报与提交回执备注。
- 夜链断档由会话续接的首会话核出，后台派补跑 agent 补该日，一次一天。
- 周段断档由周缺勤钩子（今天周一而上周归档件缺失）核出，补跑目标日为上周日；补跑时先确认日链已闭合。
- 周段被拒或中断，落账写明命中项或中断步与已完成步清单，照常提交并释放锁。
- 通信区增量收取出错不阻塞，未处理的并入下一夜补读。

**并发**：事务锁与持锁校验见 §4.8 前的锁机制说明（§5.8 一并给出）；完成只认提交回执，不认其他任何标记。

## 7 · 耦合：三个系统靠什么咬合

§4 到 §6 分开讲了三个系统。分开讲是为了讲清内部机理，但读者看完三章会有个合理的疑问：为什么不能拆成三个独立工具？

答案在接缝上。三个系统之间没有共享内存、没有函数调用、没有消息队列，只有 **skill 的输入输出契约**：一段流程写成 skill，声明它读什么、写什么、什么条件下停手、失败时留什么证据；另一段的流程据此接上。接缝因此是可替换、可单独测试、也可以只读契约就理解另一半的。

这条设计选择有一个直接后果：**PGL 的可复用性来自接缝被写成 skill，不来自三个系统本身。** 三个系统各自的内部逻辑换了用户就得重写；接缝却可以在换运行时、换用户、换领域时保持不变。

### 7.1 五个接口

```text
          ┌──────────────┐
          │  工作系统     │  文件网络：结论、推论链、流水、身份层
          └──────┬───────┘
       写入门  │   │  读取
          ┌──────▼───┴───┐
          │   loop 系统   │  目标、条目、对账、计划、推送
          └──────┬───────┘
       回执   │   │  证据
          ┌──────▼───────┐
          │  代谢系统     │  两池、毕业、事务
          └──────┬───────┘
                  │  毕业产物（规则 / skill / 身份层）
          ┌──────▼───────┐
          │   施工通道    │  编译、部署、审计、发布
          └──────────────┘
```

| 接口 | 方向 | 传什么 | 契约写在哪 | 断了会怎样 |
|---|---|---|---|---|
| **I1 写入** | loop / 代谢 → 工作系统 | 写入载荷（目标文件、节、层级、要点、关联指针） | 写入管道与各区正典（§4.7） | 书记三闸拒写并回报应下沉的去向；拒写不静默 |
| **I2 读取** | 工作系统 → loop | 项目入口、推论链、全局状态、流水 | 读取管道（§4.8） | 读不到就写「无」，不脑补；缺口进简报 |
| **I3 对账证据** | loop → 代谢 | 日节点回执（偏差、计数、健康读数）、白天纠偏行 | 夜链步序（§6.3）、记忆正典的提取来源表 | 回执缺失记零并留痕，不阻断 phase B |
| **I4 装配与投递** | loop → 投递端 | 推送包（JSON + 五节正文） | 推送装配与机械核（§6.5） | 包缺时投递端转达「计划未就绪」，不轮询、不补推 |
| **I5 毕业** | 代谢 → 工作系统 / 施工 | 剥壳后的身份层描述、新 skill、新行为规则 | 判型分流与蒸馏（§5.5）、施工通道（§8.1） | 毕业候选只生成、只留账；写入排在解锁之后 |

### 7.2 为什么必须写成 skill

夜链是这套系统里耦合最密的动作：一个定时任务里先后调起七个流程。它们的接法是 skill 套 skill：

- 日级流程在第 8 步调周级流程；
- 周级流程在第 6 步调季度检测；
- 月节点挂在周级流程返回之后；
- 每一次装配与每一次对账各是一个独立 skill。

这样接的三个好处，都在真实故障里验证过：

**每一段可以单独测。** 日节点的对账逻辑换一次，只跑日节点就能验；不用把整条夜链跑一遍。

**每一段可以单独失败。** 任何一段的任何缺口都不阻塞下一段，phase B 失败不回滚 phase A。如果协同写在代码里，这个隔离要先造一套调度才拿得到；写成 skill，隔离是默认的。

**每一段可以单独替换。** 换运行时、换投递渠道、换外部台账系统，只改接那一端的 skill，三系统的内核不动。

代价也有：**接口不在一个文件里，而在两侧 skill 各自声明的输入输出里，两侧说法不一致时不会有编译器报错。** 所以每个接口两侧各写一遍契约，由一项机械核（产物不变量检查）来对账。代价是真实的，这套系统用「同一件事在两侧各留一次收据、再由审计比对」来补偿。

### 7.3 三类耦合的松紧度

| 类型 | 例 | 松紧 | 失败的影响半径 |
|---|---|---|---|
| 同一次事务内的耦合 | 工作固化与记忆代谢同包、同锁、同提交 | 紧。共享转写包与提交回执，一段失败另一段按隔离规则继续 | 本夜 |
| 同一节拍上的耦合 | loop 的对账结果作为次夜代谢的输入 | 中。中间隔一个推送包与一份回执 | 次日 |
| 跨节拍的耦合 | 代谢毕业产物改变 loop 起草计划时读到的身份层 | 松。改动生效在下次会话启动 | 下一个周期起 |

松紧度决定了一个修正要多久才能在系统里显形：紧耦合的改动当夜可验，松耦合的改动要等到下一个启动周期。设计和排期时按这个顺序排。

### 7.4 越界的特征

接缝最常破在三个地方，都被写成了可检查的特征：

- **绕过写入管道直接落盘。** 表现为 INDEX 层文件里出现绝对路径、hash、版本号；或同一个文件出现两个写入方。
- **绕过回执宣告完成。** 表现为一段流程自己有产出、下一段读不到收据。
- **绕过毕业直接改身份层。** 表现为对话里的一句评价被直接写进用户档案或 agent 人格。

三条各有对应的机械闸（§4.7、§5.8、§5.5），闸报红时不以降级处理，按失败处理。

## 8 · 递归与施工：系统怎么改自己

### 8.1 递归的三个环节

「系统改自己」不是一句比喻，它有固定的三段：

```text
① 产生信号        ② 形成提议            ③ 落地
运行中暴露的失败 → 递归提议（带预测与到期日）→ 参数调整 / 规则改写 / 新 skill / 新身份
```

**第一段：信号从哪来。** 四个来源，全部机读：

- **对账偏差**。日节点把每条未达预期的条目归到四个原因类之一：计划、执行、外部、目标变动（§6.4）。
- **流程偏差**。缺计划、缺预期、缺执行流水、执行流水不符——这些不是条目没做到，是流程自己没走对。
- **纠偏行**。用户对当天计划的条次、内容或优先级给出意见，agent 当场改写并记一行归类（§6.8）。
- **环境预测误差**。流程跑完之后被测试判红、被审计判 FAIL、被写入闸拒写、交付迟于承诺、事后被改判返工（§5.5.4）。

**第二段：什么时候形成提议。** 按 §6.6 的五类触发判定。关键是阈值：单次偏差只记证据，同类信号反复出现才构成提议。反复的判据写死在参数表里，不靠判断。

**第三段：提议去哪。** 按生成者类分流：

| 类 | 含义 | 裁决 | 落地方式 |
|---|---|---|---|
| A | 用户的目标与裁定 | 用户 | 用户给出取值后，作为执行条目进次日计划 |
| B | 方法与规则 | 主 agent 按常设授权 | 执行条目 → 改 skill 或正典 → 编译部署 |
| C | 环本身 | 主 agent 按常设授权 | 同上；机制类提议全部归此类 |

阈值校准不论生成者类，一律交用户裁决（§6.6.5）。

### 8.2 落地：施工通道要解决的三个问题

提议被采纳，只是得到一句「该改成什么样」。把它真正装进运行中的系统，要解决三件事：

1. **改哪一份。** 同一套规则在磁盘上至少有三个形态：共享模板源、编译后的运行时、以及在跑的现役文件。改错一层，下一次编译就把改动冲掉。
2. **改了会不会崩。** 改的是正在用的规则与脚本，没有测试就跑，坏了也不知道坏在哪一步。
3. **怎么撤回。** 出了问题要能退回上一个状态，且退回之后不影响已经发生的业务。

施工通道按这三件事组织，核心是三条纪律：**改动只发生在可丢弃的副本里；每一步留下可机械重算的回执；上线后由独立核验与变更日志收尾。**

### 8.3 单向编译

共享模板源是唯一权威。每台机器用它加本机配置，单向编译到自己的运行时目录。

```text
共享源（模板 + 脚本 + 测试 + 清单）
   │  编译（单向，不允许反向漂移）
   ▼
本机运行时（.claude / .codex 等）
```

**编译有五类单元**，各有固定的合并语义：

| 单元 | 语义 |
|---|---|
| 单文件模板 | 全文渲染，占位符替换，不做合并 |
| JSON 合并 | 共享值覆盖同名键，本机独有键保留 |
| 受管策略键 | 只 patch 白名单内的键，其余本机配置不动 |
| 受管标记块 | 只替换标记之间的内容，标记之外本机独占 |
| 目录树 | 逐模板渲染；支持排除规则与适配器 |

**编译前先自检源信封**：把清单里记录的文件集合与磁盘重算的哈希比对，有缺、有多、有改就停，要求先刷新清单。这一环防的是「改了源却没刷新清单就编译」——那会让产物与清单永久不一致。

**零漂移的定义**是两件事同时成立：编译的检查模式报告零处变更，审计报告零类发现。二者用的是同一份期望产物计算，所以「编译说没变、审计说变了」这类矛盾在结构上不可能出现。

**改共享源本身时只刷新清单，不用反向发布。** 反向发布会把本机整个运行时的状态灌回共享权威，改一个脚本顺手把这台机器所有本地漂移都推上去。

**模板与现役必须同轮改。** 只改现役不回写模板，下一次源变化后的整轮编译会把现役覆盖掉。

### 8.4 施工主链

一次成批的改动走同一条链。链的形状是十二步、八个判断节点、八个机器段，每一步的产物都落成回执。

```text
路由 → 建暂存 → 规格与耦合清单 → 分区 → 并行施工 → 整合
     → 基线比对 → 分区检查 → 部署门 → 三方分类 → 回写 → 编译
     → 部署核验 → 工作库记账 → 汇报
```

**暂存。** 每批一个目录，内含源的两份完整副本：一份只读作基线，一份是唯一施工面。建目录时复制前后各算一次源指纹，两次不同即整批作废——说明复制期间有别的执行体改了源。

**基线。** 全量测试在施工副本上连跑两遍。两遍读数不同的失败项单独列为**现场项**：读现场库的测试，读数随现场浮动。现场项要有证据才能登记，且不进判定；没有证据的失败一律按新增失败处理。

**规格与耦合清单。** 规格写明决策来源、范围、跨分区必须逐字一致的口径表、分区表、可机械判定的验收口径。耦合清单把被改的键与词在各个文件里的**每一个出现点**记下文件与行号，并单列「被测试钉死的字面量」——步骤号、步骤标题、探针名、命令块顺序、行数上限。

**分区与并行施工。** 按文件切区，一个文件恰属一区；同一口径的机械件、它的测试、审计探针同区。每个分区交一个 sub-agent，brief 里带本区文件清单、口径表、硬约束、测试命令与基线读数。并行施工有活性契约：派发后十分钟内看不到进度就催办，连续两个窗口无新进展判失联，主会话最多等两个无进展窗口，同一分区最多重派一次。

**整合与区分力验证。** 主会话独立证明新增的闸能红：在新增闸上改坏至少两处，对应测试必须转红。这一步不能外包，因为改测试的人和写测试的人是同一个时，他会无意识地写一个总能通过的测试。

**部署门。** 五项同时成立才开门：夜跑锁空闲且距下一次夜跑起点不少于三十分钟；前两步审计退出码均为零；对端配置快照已取；工作库载荷已就绪；上线时点早于下一个依赖新口径的夜跑。

**三方分类与回写。** 每个改动路径按「基线 / 施工副本 / 源现状」三方分类为待落地、已落地、漂移、禁写。漂移的处理原则是**绝不覆盖别的执行体对源的并行改动**：能无冲突合并就合并，合并后在新基线上重取测试基线并重测；有冲突就停手，按证据判断改动的来源，交对方裁决或交人。

**编译与核验。** 刷新清单 → 编译 → 按快照恢复受守卫的配置 → 只读复核零漂移。部署后隔两个监视周期再核一次配置哈希（监视器会再编译，改写属预期）。

**核验七项**是必过项：自检、步骤号绑定、架构新鲜度、巡检、加载链、编译零漂移、对端配置哈希。缺采集的必过项记失败——「没跑」不得算「过了」。

**记账。** 最后一步把改动写进工作库：写前快照 → 交写入载荷给书记 → 核对每项都有回执 → 终核 → 汇报。

### 8.5 事务与停摆

回写源与编译运行时是两个效果边界，各自是一个事务，共用同一个事务内核，时序固定：

```text
意图 → 回读 → [效果] → 收据 → 回读 → 提交 → 解锁
```

三个关键设计：

- **先回读再动手。** 首次回读已经是「已落地」，就跳过效果，只补收据。这处理的是「上一次跑到一半被杀」的情况。
- **未知状态不重放。** 回读结果不可判定时，停到待对账状态，不重放、不解锁。盲目重放一个已经生效的写操作，等于把改动做两遍。
- **围栏单调递增，解锁后保留。** 新一次取锁的围栏恒大于任何旧持有方；旧持有方被接管后再写，在写前核围栏处被拒绝。

停摆的处置按原因分流：锁被夜跑占着就等；计划变了就重测后重出计划；有漂移就走合并；围栏失效就停手查状态。每一条都对应一次真实事故。

**字节码缓存是这里最隐蔽的坑。** 解释器按源文件的修改时间（取整到秒）与大小判断缓存有效，同长度改动落在同一秒内会读到旧代码，整组测试照绿，改坏的代码看上去「没被抓到」。所以工具链先清缓存目录与前缀镜像目录，再以禁止写字节码的方式启动，并把缓存前缀指向一个不存在的目录。

### 8.6 审计器族

规则写在 Markdown 里给 agent 看，而 agent 会漂移。所以每条可机械判定的规则都配一个脚本兜底。

| 脚本 | 管什么 |
|---|---|
| 加载链审计 | 正典存在、加载链与上游、上下游可达与双向一致、孤儿、INDEX 预算、层级边界、路径字面量、正典 frontmatter、可达性 |
| 运行时审计 | 两端名册对称、已部署 agent、hook 注册、模型与沙箱、skill 路由白名单、跨端路径与记忆边界、身份权威源 |
| 巡检 | 锚点死链、通信区行数、frontmatter 漂移、推论链断头节点、改了未记日志、标签出处 |
| 记忆审计 | 两池结构与字段合法性、容量分区、状态值、逾期未衰减、跨池重复、衰减时钟 |
| 定时链探针 | 按逻辑日逐步骤核对声明的产出在不在 |
| 写入类 skill 闸 | 产物不变量：推论链节点字段、加载链区块 schema、项目登记账实、同层项目数上限 |
| 架构说明审计 | 名册表对现役名册、闸表对磁盘闸集合、禁止复制易失值 |
| 单核部署审计 | 一个核心源绑定两端、适配器只含声明字段、两端编译产物逐字节一致 |

三类闸的形状差异是设计上的要点：

- **定时链**可以问「今天第 N 步跑了吗」，因为它每天必跑一次。
- **按需触发的 skill** 问同一句话只会得到「不适用」——今天没人调用它，这个闸结构上不可能失败。判据换成**产物不变量**：不问跑没跑，只问凡是它写下的东西是否都满足它自己声明的格式。
- **描述层**用更强的一招：不检查「复制的数字是否最新」，而是**禁止复制**。数字留在权威源里，描述层只留指针，于是没有可过时的东西。

**绿的定义**是退出码零，且这个零的含义由脚本自己声明。本趟新造的失败一律当夜修到绿，不得以「可忽略」放宽。存量失败（不是本趟写入造成的）可以登记到待裁项、写明清偿排期与执行者后继续；**排期到期未清即停机**：停当前链、报用户、不自行顺延。

### 8.7 区分力验证

> 闸、扫描、自核在报绿或零命中之前，必须先证明它在该红的时候会红；未证前不采信，按失败处理。

判断方法只有一句：**如果被检查的东西现在就是坏的，这个检查会不会输出任何东西？** 答案是不会，它就不是检查，是安慰。

四种落地形态：

1. **变异测试**：把源复制到临时目录，按清单改坏一处（旧值必须在文件里恰出现一次），跑指定测试，测试必须转红。测试照绿说明测试本身有缺口。
2. **哨兵自检**：拿一个「确定什么都没发生」的远过去日期跑闸，若全绿说明探针恒真；同时拿今天跑，若全不适用说明这个闸没有任何可判项。
3. **反打正典**：把正典对应格里的数故意改一档，闸必须按新格判定；篡改锚点字样后再跑，闸必须报错而不是继续用旧读数。
4. **空集检查**：作用域为空、命中集为空、输入清单缺失，三种情形必须各自可区分。**空集比报错更危险，因为它看起来是通过。**

这套方法在对闸自身的回归测试里是硬要求：每修一次闸，就加一条针对该假绿形态的用例。否则修完的东西下次还会以同样的方式坏掉。

### 8.8 流程沉淀为 skill

「把经验变成 skill」是递归最重的一环，也是施工与代谢的接点。

```text
流程情景（夜里记录） → 蒸馏候选（同领域三次、两个对象、无现役 skill）
  → 三路独立蒸馏（一致 / 多数 / 各异） → 成稿（元技能） → 部署（施工主链）
```

**元技能**是这条通道的编译器。它把一段长链流程切成判断段与执行段的交替序列，逐段标出操作类型，并为每个操作配一组最低强断言：

| 操作 | 最低断言族 |
|---|---|
| 取数 | 来源收据、结构符合、条数与哈希 |
| 过滤 | 输出是输入的子集、谓词可重放、被排除项可枚举 |
| 映射 | 键与行保持、字段变换可重放 |
| 连接 | 键覆盖、基数、未匹配集合、连接后取值可重放 |
| 分区 | 并集完整、两两不交、分桶规则可重放 |
| 汇总 | 明细可重算、合计对账、每桶独立可枚举 |
| 渲染 | 行列对账、表内统计对账、输出字段覆盖 |
| 交接 | 产物哈希、结构符合、接收方回执 |

核心机理一句话：**产物的守恒性质与产物的规则应用正确性正交。** 并集完整、桶间互斥全部成立时，分桶规则用错了照样全绿；合计等于输入数时，输入本身错了照样全绿。所以每条断言都要配一个必须被它自己拒绝的变异样本。

**验收分四层，各出各的结论**：宿主层、契约层、入口绑定层、行为与恢复层。较高层的成功不覆盖较低层的失败，未运行写「未运行」。装到目标宿主之后另有部署结论：排程类或状态类 skill 至少要从真实入口完成一笔获授权的真实事务并回读终态；只跑过隔离测试时，只能报「代码已安装，生产闭环未验证」。

**行为层用黑箱测**：派三路互不可见的 sub-agent 各跑同一个真实任务，逐判断段比对路由。三路走不同分支就回炉；三路全收敛只记「未测出分歧」，不记「可复现」——没有参考答案时，三路一致也可能是判据本身错了或三路共享同一偏置。

### 8.9 发布线

私有系统到公开模板是单向、渐进、脱敏的，且不经编译链：

```text
私有工作系统 ──抽象与脱敏──→ 公开核心 ──+ 各端适配──→ 各公开仓
```

发布闸的四条判据，都是从真实事故里逼出来的：

| 机制 | 判据 |
|---|---|
| 开关 fail-closed | 发布模式下调时缺脱敏清单即判失败，不当跳过。只有一个「跳过」处置是漏洞：干净 clone 与持续集成里都没有清单，唯一的内容扫描被静默跳过，而套件报通过——「绿」与「查过了」从此脱钩 |
| 清单在仓外 | 只认环境变量指向的仓外路径。把真实标识写成字面量放进闸源码，等于为了检查泄露而把要查的东西完整发布一遍 |
| 扫描面全覆盖 | 每一个会被推送的文本文件，不排除任何文件，包括闸自己的源码 |
| 大小写与豁免顺序 | 统一折成小写后比对；已公开的标识符在折叠之前剔除（折叠后无法再按大小写区分私区代号与已公开名），顺序反了会让闸恒红，而恒红等于没有闸 |

「空集比报错更危险」「假阳性对照必须存在」「判据要能在该红时红」——这三条通用教训各自在发布闸里都有对应的测试。

### 8.10 变更的四步闭合

任何协议、架构、skill、hook 的变更走同一套：

1. **改权威源本体。** 一条规则只允许一个权威源。
2. **扫引用网络。** 用被改条款的关键词检索，范围覆盖共享源、编译产物、记忆文件头部、主文档；规则的键或数有实现的，实现与测试一并列入。
3. **同轮更新版本与日期。**
4. **记一条变更日志。**

第二步是最常漏的。改名尤其危险：它看起来只是一次移动，实际上同时动了正典声明、入口层指针、skill 引用、巡检脚本常量与两端模板。

配套的**取键取数通则**：脚本、闸、探针与测试在实现正典规则时，用到的键与数都回到声明它的正典取。能运行时读就读；只能写成常量的，常量旁注明出处，并配一条测试核对该常量与正典原文一致——正典改数后该测试即红。

## 9 · 授权、风险与故障恢复

### 9.1 S / N / C 三级

每个动作按可逆性与影响面定级，级别决定 agent 要不要先问用户。

| 级 | 含义 | 典型动作 | 执行方式 |
|---|---|---|---|
| **S** · 静默 | 低风险、可逆、局部 | `_current.md` 单行追加；审定原话的逐字转录 | 直接做 |
| **N** · 通知 | 中风险、影响可见，或需要事后可见的回执 | 记忆池条目级操作（代谢、直升，`MEMORY_LOG` 留账，提交回执随晨间推送转述）；通信区维护；skill 路径调整；项目 `_overview.md` 结论节（覆盖走幂等键与覆盖收据）；`status.md` 与 `weekly.md` 更新 | 直接做，事后回报 |
| **C** · 确认 | 高风险、不可逆 | 修改 skill；季度归档执行；删除或覆盖整份记忆、身份或权威源文件 | 告知，等用户确认 |

记忆池条目可以自治，理由是错误有界且会自愈：一条模式错了，会被后续观察击穿，击穿触发修订，容量上限又逼出竞争；`MEMORY_LOG` 提供事后审计，用户随时可以推翻。

### 9.2 常设授权

三级是默认配置，用户可以按信任程度调整。私有系统的现役配置是一份常设授权：

- **改由 agent 裁决并执行、事后回报**：待裁项、正典 / 协议 / skill 变更（走四步闭合，§8.10）、季度归档执行、身份层与 skill / 行为规则的毕业写入、节点闭合与推送装配中产生的待裁项、项目互通与跨项目引用、归档整个项目。事后回报必须包含裁决、理由、动作和撤回方式，并闭合对应的待裁项。
- **身份层（USER、SOUL、入口文件）修改降为 N 级**：依据必须是满足毕业条件的候选，或用户原话；单次对话里的其他内容不直接改身份层。
- **仍须用户确认**：删除整份记忆或身份文件、任何归档件或项目文件；智能异常停机与恢复；定时任务排程变更；对外发布与发送；强制抢占事务锁、确认接受断档。
- **夜跑事务内的 C 级事项**在事务内裁决，涉及改文件的执行放到事务解锁之后。
- 常设授权只对授予它的那一端有效。

### 9.3 故障恢复

| 症状 | 处理 |
|---|---|
| 启动序列文件读取失败 | 告知路径，请用户确认重建或跳过 |
| 记忆写入与权威源冲突 | 停止，呈现冲突，等裁决 |
| INDEX 层超预算 | 超出部分下沉到 CONTENT，INDEX 留指针；禁止截断，禁止压缩措辞充数 |
| 加载链审计非 exit 0 | 修到绿再继续；不得以「可忽略」自行放宽验收标准 |
| 存量 FAIL（不是本趟写入造成的） | 判据：该 FAIL 的路径不在本趟落盘清单内。登记到待裁项文件，写明清偿排期与执行者，才可以带着 FAIL 继续；排期到期未清即停机：停当前链、报用户、不自行顺延。本趟新造的 FAIL 一律当夜修到绿 |
| 专注区有文件未纳入 `_current.md` | 周级做梦的账实核对处理，遗漏按 N 级告知 |
| 夜跑缺勤（工作固化或代谢断档） | 当日首个会话核对昨夜事务，后台派补跑 agent，逐日补、一次一天（§5.8.5） |
| 同一逻辑日被两个执行体同时处理 | 事务锁互斥：锁被占用（`HELD`）一律停手报处置建议，不抢占；持有方会话闲置超过 2 小时，由锁闸机械接管（`TOOK_OVER`）；不经锁闸的写入，写前先核对持锁（`NOT_HOLDING` 即停手，不写，不解锁）（§5.8.2） |
| 语义池持续满载不降 | 周级池代谢容量强制清理；持续不降则调阈值（走四步闭合） |
| 情景池活动与复审态超过红线 40 条 | 机械规则：当夜代谢按四键排序清到 ≤ 40，周级做梦复跑；不询问、不挂待裁项（§5.4.5） |
| hook 报错 | 告知用户检查宿主的 hook 配置 |
| 疑似智能异常 | 用户判定「这不是它」或「停，感觉不对」：当前会话立即停止所有写入，转只读，等授权 |
| 智能异常恢复 | 用户授权后，定位异常会话的起点，把期间触碰过的文件全部恢复到会话开始前；期间的所有改动一概不作数 |

最后两行是整套授权模型的兜底：agent 的行为是否还像它自己，最终由用户判断。一旦用户判定异常，系统不靠 agent 自证，直接停写并回滚。

## 10 · 运行时纪律：生成期的标准

四个子系统管环怎么转、经验怎么沉淀、知识怎么存取、系统怎么改。还剩一项根约束没解决：生成期的标准滑动（§1.1 第 4 条）。滑动发生在生成过程内部，存读架构管不到，事后审计也来不及，所以少数高风险纪律必须在每次生成之前就位。

常驻注入最贵，常驻位因此只配给「必须在生成前生效」的内容，也就是会改变 agent 下一步行动的纪律；其余一切按需披露。这些纪律没有预设的纪律库，每一条都来自真实失败，经代谢提取后毕业为行为规则（§5.5）。

### 10.1 思考协议

四步循环，内化执行，不输出步骤标签。协议在遇到问题时启动，两类入口同等触发：

- 每段对话内化执行（默认入口）；
- 执行过程中遇到问题：在 skill 流程里、跑工作流时、敲某个动作时撞上新问题、歧义或缺口，就地从第 ① 步起处理这个问题，处理完再回到原执行点。

**① 分析**

- 明确这一轮要做什么：问题类型（事实查证 / 方案设计 / 理论推演 / 执行任务 / 闲聊）、完成标准、关键词的词义边界。
- 判别对话态：讨论态还是执行态。未收到「开始做 / 动手吧 / 执行」这类显式信号，默认讨论态，不动文件。
- 有歧义先问，不用生成能力填补理解缺口。

**② 检索**

- 以当前问题为导向检索，带着这一步要解决的具体问题去找事实。
- 必须检索、禁止凭记忆输出的内容：外部事实、文献结论、数据、版本号、定价、日期、API 行为、术语的权威定义。
- 按检索类型派单：学术文献、机构与人物、通用网页与对话回溯、公开背调各有专职检索 sub-agent；本地文件的批量读写派书记 sub-agent。
- 检索结果充分铺开再用，不截取单句断章取义。
- 纯逻辑推断、已知信息的组合，直接进第 ③ 步。

**③ 推导**

- 反例先行：先列「什么会推翻这个结论」，再列支撑论据；找不到反例要声明。
- 开放问题、归因、诊断类问题，必须设 ≥2 个竞争性假说，分别给出判别证据。
- 推理节点完全拆开，路径外显，每一步都能被单独攻击。
- 标准滑动自检：同一判定标准是否在本轮内从严到松偏移；靶子是否从「判断 X 是否成立」换成了「为 X 找支撑」；标准没变，但应用环节是否软化。命中任一条即有合理化嫌疑，回到反例重新推。
- 推导中发现新的检索缺口，返回第 ② 步。

**④ 执行**

- 收敛判据：没有未回应的反例、没有未检验的关键假设、已确认执行态。三者齐备才动手。
- 承诺即调用：输出里含有「我现在读 / 改 / 写 / 派 / 继续」这类执行承诺时，同一条消息必须带上对应的工具调用；无法调用就显式报告阻塞点，禁止以纯承诺结束回合。
- 长链批量执行：先建议压缩上下文；机械性的批量读写、大范围扫描、日志落盘打包派书记 sub-agent，主会话只留裁决。
- 执行中遇到新问题，停手回到第 ② 步：新问题意味着信息缺口，先取事实再推导，不带病推进。
- 用户说「直接执行」时，可以从第 ① 步跳到第 ④ 步。

**理论研究扩展**（第 ③ 步收敛后）：主动提出对立假设、边界案例与跨域连接，用探索性语气。

### 10.2 底线与硬禁止

- **推理质量底线**：听到立场时，禁止为它生成支撑论据；理解有缺口先提问；开放问题给推论性判断，不列一排选项让用户自己选。
- **区分力验证**：一道闸、一次扫描或一次自核报绿或零命中之前，先证明它在该红的时候会红。未证明前不采信，按失败处理（§8.7）。
- **现读核实**：对平台、线上环境、远端系统的当前状态下结论时，本回合必须有一次指向该系统的现读工具调用及其输出；没有现读回执的一律标「未核实」，不进结论，也不据此推进。
- **硬禁止**：第一句直接认可；第 ③ 步未完成就执行；未检索就输出学术结论；为立场生成支撑论据；用泛化原则做修饰性论证；凭记忆断言自己说过或没说过什么（必须回看转写核实）；开放问题甩选项给用户。

### 10.3 三类失败与纪律的对应

早期版本把三条常驻纪律称为「反合理化三角」。它们在现役形态里并入了思考协议与风险分级：

| 失败形态 | 防的是什么 | 现役落点 |
|---|---|---|
| 用静态推理代替运行时的事实核查 | 地面事实缺位 | 第 ② 步的必须检索清单、现读核实 |
| 把工程惯性当成用户授权 | 越过授权范围 | 讨论态 / 执行态判别、风险分级（§9） |
| 同一推理链内判定标准从严到松 | 合理化 | 第 ③ 步的反例先行与标准滑动自检 |

行为规则层还承载由毕业得来的其他生成期规则（例如表达纪律），具体内容因用户与 agent 而异。

## 11 · 演进史：每个结构对应一次失败

PGL 没有一处是先验设计正确的。它的每个核心结构都由实际使用暴露的失败逼出来，改法记录的是一条案例链。这一章按时间顺序列，每行是一次真实故障与它逼出的结构。

本章是全书唯一以过程追踪为职责的地方：它记录的是「曾经怎么坏过、因此改成什么」，所以保留了旧形态。

### 11.1 早期：从「记什么」到「怎么读」

起点是一套公开的个人 agent 记忆模板：四层记忆加惊奇度驱动写入。它指出记忆应当由偏离信号触发、系统需要身份层与工作层分工。两处不彻底：惊奇判定没有稳定预期作参照，不同会话的判定互相矛盾；它完全没有回答「知识怎么读回来」，文件之间怎样引用、规则权威源怎样不被复制体稀释。

| 失败模式 | 逼出的结构 |
|---|---|
| 惊奇度直觉判定不一致、无对照基准 | 模式字段化 + 一组持久参照系做隐式比对 |
| 候选池一周内从 17 条涨到 32 条、无一条毕业 | 默认遗忘 + 两轴窄入口（命中且中性不提取） |
| 身份层混入日志字段与错位条目 | 判型分流 + 剥壳纪律：只留稳定描述 |

### 11.2 中期：从「存」到「治理」

| 失败模式 | 逼出的结构 |
|---|---|
| 同一推理链内判定标准从严到松 | 少数高风险纪律启动注入，在生成前就位 |
| 语义池 8 条里 6 条是项目内容污染 | 升格三道闸：领域无关性、对照人测试、逐条判 |
| 规则复制了 3 到 5 份，累积 17 项边界矛盾 | 单一权威源铁律 + 全限定指针 + 锚点可验证 + 变更四步闭合 |
| 实时写入管线把成本付在白天上下文中，产出却是夜里必然重做的低保真索引 | 昼夜分工：L0 只读转写、实时写入层整体拆除、夜间集中代谢 |
| 毕业出口单口径平列，没有蒸馏工序；身份层条目是描述格查找表，生不出未列举情境的行为 | 判型分流 + 三路独立蒸馏 + 四条毕业出口决策树；身份层改为「机制句 + 世界观假设 + 触发情境 + 预测动作」四件套 |
| 排程把逻辑日期误填进物理钟字段，两次空放 | 时间感知升为入口层头部声明，排程后加核验硬步骤 |

### 11.3 近期：工作环接入之后

从工作环接入开始，失败集中在「两套系统怎样同源、时序怎样不出错」。

| 失败模式 | 逼出的结构 |
|---|---|
| 环起算日之前的日子无限重跑，夜链原地踏步 | 零会话日闭合路径 + 环起算日参数 |
| 会话转写只收用户与助手两类回合，用户在生成过程中插的话整批漏掉（一天漏十八条） | 从转写记录的附件类型回收中途插入的话，单独标注跨端消息 |
| 审定写成裸编号被判定无效、逐条丢弃 | 条目键改为五种合法形态，错误提示直接给出正确写法 |
| 夜跑把整理出的十几份笔记当完成收工，又三次自写完成标记 | 完成只认提交回执，不另写任何完成标记 |
| 抽整日转写撑爆上下文 | 锚点切片：只装以用户原话为锚的三段，实测消息数从 165 压到 35 |
| 事务锁放进产物目录，被产物清理逻辑扫走 | 锁移到产物目录之外；判活的唯一证据改为持有方会话转写的最近写入时间 |
| 日计划连续四天只显示被卡住的事项，推进中的任务不进次日计划 | 活跃任务表 + 次日草稿按收口日选模板 + 现状核对 |
| 白天对计划纠了偏，夜里代谢读不到 | 纠偏行作提取来源之一；推送侧也读最近七日的纠偏用作排序输入 |
| 校准信号要等次日才入池，入池后白天也看不见 | 即时微代谢（只写情景池、每逻辑日至多五条）+ 纠偏摘要窄注入（至多八条、一千六百字） |

### 11.4 施工侧的失败

施工侧的故障有一个共同特征：**改错了不会报错。**

| 失败模式 | 逼出的结构 |
|---|---|
| 监视器指向已迁移的旧路径，每六十秒失败一次，累计数天，自动编译链完全失效而无人察觉 | 安装器从脚本自身位置推导路径；部署核验把监视器在位列为必过项 |
| 模板旧于现役时打开自动应用，直接用旧模板覆盖新现役 | 先逐份回填模板再开监视器；模板与现役同轮改 |
| 锁文件与产物同目录，被产物清理逻辑扫走 | 锁落在产物目录之外的同级目录 |
| 辅助目录混进产物扫描，其字典序大于任何日期名，被下游当成一个日期目录 | 按日期形状过滤，不靠排序位置 |
| 审计器缺来源，造出成片假红 | 审计器自身有回归测试，每修一次闸加一条针对该假绿形态的用例 |
| 审计器的前置条件把断言吞掉（产物目录不存在就直接返回通过） | 同上；判据改为「被检查的东西现在就是坏的，这个检查会不会输出任何东西」 |
| 发布闸在干净 clone 里缺清单，唯一的内容扫描被静默跳过而套件报通过 | 发布模式下调时缺清单即判失败；仓外清单；扫描面全覆盖 |
| 同长度改动落在同一秒内，解释器读到缓存的旧字节码，变异测试全部假绿 | 清缓存目录与前缀镜像目录、禁止写字节码、缓存前缀指向不存在的目录 |

### 11.5 方法论命题

**长期代理系统无法被一次设计正确，只能被持续使用纠正——所以系统必须自带被纠正的通道。**

这条通道由两部分组成：记忆代谢把失败变成新的判断与纪律；变更日志记录结构改了什么、为什么。系统用自己的记忆系统记住自己的失败。

第四章到第八章的每个机制，都能在这张表里找到它出生时的那次故障。这也是「为什么必须是三个系统」最硬的回答：不是设计者选了三个，是失败按三类堆起来，每一类都需要一套自己的状态对象与节拍才能收敛。

## 12 · 未接通与开放问题

说明书写到这里，还留着若干没有接上的边。它们是系统的现状，不是待办清单的承诺。

**机制已设计、消费端未接通**

- **活跃任务表**：规则声明了入表判据、五列、消费方式与逾期处置，夜链的写入点也写了，但推送装配、夜链与日节点对这张表都没有取数代码，现有推送条目全部来自日段引用，「逾期满 3 天自动置搁置」只有规则，没有机械执行。
- **周一条目的现状核对**：目标日为周日时次日不起草、不核对，周一条目由下周拆解与周日结转承接，前提核验在周一缺位。

**环在转、某条出口还没转过**

- **递归**：五类触发里，实际产出过提议的只有「计划校准」与到期项两类；「机制」「阈值校准」两类至今零实例。已登记的提议大量失效（针对的周或月已经归档），承诺类判断的样本数为零，命中率基线还没有数据。
- **阈值校准**：机制参数的初值表已就位，月节点也有判定流程，但多数参数尚未达到样本下限，校正在纸面上完成、在数据上还没开始。

**归因粒度不足**

- 日节点的对账只做逐条归因（计划 / 执行 / 外部 / 目标变动），不做跨日的同类条目履约率聚合。因此「预期一贯偏乐观」这类普通原因判不出来，「外部」容易成为终止符。

**生产样本不足**

- 新版月节点口径尚未在生产夜链里完整走过一遍；月度指标多项依赖用户或外部系统输入，首月预期大面积「需外部输入」。
- 外部镜像的拉取长期缺数据，台账快照停滞；对等端的执行流水稀少，通信区补证经常一档空转，「缺执行流水」成了高频流程偏差。

**理论层仍开放**

- 渐进式披露的节点载荷是否需要统一 schema，还是按节点类型分型。
- 决策充分性（「读到这一步能否做出正确的下一跳判断」）怎样建立可回放的测试集。
- 双链互引采用稳定锚点还是显式 ID，两者并存时如何机械验证唯一命中与完整还原。
- 工作记忆里「覆盖、归档、废止」三种状态语义怎样落到各区域的正典。
- 理论版本与运行时版本的兼容矩阵放在哪里。
- 通信区的项目键是否直接复用项目相对路径，怎样处理项目移动与嵌套容器。
- 候选池的命中率、误报率与毕业周期至今没有量化观测，「代谢健康」仍靠人工判读。
- 根约束与机制的对应关系只做了正向推导，尚未逐机制反推「若这条约束不存在，该机制是否仍然必要」。

### 13.2 部署方式

模板不提供安装脚本。在宿主里把模板仓链接发给 agent，要求安装或迁移；agent 按入口文件顶部的部署协议，自己完成下载、占位符替换、旧版本检测、旧数据备份与迁移、部署后验证，最后从入口文件里删掉这一节协议。

安装脚本假设用户会读命令行、能处理路径权限、能调试失败的脚本；PGL 的目标用户多数不满足这些条件。脚本又是单向的，处理不了「本机已经有一套旧版本在跑」的迁移场景。写成文字契约后，安装与升级是同一条 agent 可执行的流程。

首次部署后进入访谈式初始化，分三个阶段：

1. **基础信息**（约 5 分钟）：称呼、语言、时区、主要用途、隐私边界；agent 的名字与说话风格；当下处境与在推进的项目，每个项目当场建项目；作息与宿主可用性。
2. **故事访谈**（约 30 分钟）：agent 主动引导用户讲经历、项目、自我认知、价值与行为模式，可以直接读用户提供的工作文件夹并据此追问。
3. **拆解与预览**：agent 按材料密度决定建哪些身份子文件，给用户预览，确认后写入。

身份层初始只写用户明确说过的内容，不预设结构，也不建空壳文件；之后的稳定模式一律经毕业通道进入（§5.5）。

作息一项必须问。夜链读的是「昨天」的转写，而「昨天」的边界由作息决定；日界线设错不会报错，只会让每天有一段工作被归到错误的日子。agent 按作息推算日界线与夜跑时刻，与 IANA 时区一起念给用户确认，再在宿主里创建唯一一条每日定时任务，保存后回读核对。任务回读成功只说明配置已保存；首跑通过要看三类证据：宿主的定时触发运行记录、目标日的 `COMMITTED` 事务收据、同日的探针文件。

## 14 · 术语表

| 术语 | 含义 |
|---|---|
| 逻辑日 | `[D 04:00, D+1 04:00)` 的窗口。窗口内的会话转写归 D 日 |
| 日界线 | 逻辑日的切分点，落在用户的作息分界处，初始化时确定 |
| 目标日 D | 夜链正在处理的已闭合逻辑日 |
| 推送日 P | 计划送达的那一天，等于 D + 1 |
| 主 agent | 承接主会话、负责判断与裁决的 agent |
| 对等端 agent | 运行在另一套运行时上的独立 agent，承接代码与跨端执行 |
| sub-agent | 由主 agent 派出的子代理：书记（文件读写）、检索（学术 / 机构 / 网页 / 背调各一）、补跑（夜链断档补日） |
| 真身 | 一条规则或一个事实唯一现役的那份文本 |
| 指针 | 不复制正文、只指向真身的位置标记，形如「文件名 + 节名」 |
| CANON / INDEX / CONTENT | 治理层的三层：规则、入口索引、正文 |
| 工作记忆 | 工作对象的当前状态、结论、推论与流水，共享给用户与各端 |
| 预测性记忆代谢 | 从经历里提取候选 schema，经复现、衰减、统合与毕业更新未来的预测与行动 |
| episodic | 情境绑定的候选 schema 池，1–3 星 |
| semantic | 稳定 schema 的中间工作区，4–6 星，等待毕业 |
| 身份层 | 用户档案、agent 人格、行为规则与 skill——毕业的终点 |
| 毕业 | 模式从候选池进入身份层的过程，含判型分流与蒸馏 |
| 两轴判定 | P 轴（预测：命中 / 击穿 / 未覆盖）与 C 轴（校准：正向 / 反对 / 纠正 / 中性） |
| 默认遗忘 | 默认动作是不写；写入需要 P 轴或 C 轴给出价值信号 |
| schema | 「触发情境 → 行动 / 预期」的可运行模式 |
| 任务锁（in-flight lock） | 同一逻辑日只允许一个执行体处理的事务锁 |
| 收据 | 每一步落盘后留下的可机读证据，完成只认提交回执 |
| 环内条目 | 日段里编号的一条计划，最小颗粒的执行单元 |
| 计划节点 | 一条环内条目；闭合时固化结论 |
| 总表 | 本周目标总表，十列，周计划的权威 |
| 日拆解 | 总表按天分配到日的一行，格内编号的先后即当天优先级 |
| 收口日 | 一周里用来收口全部工作的那一天，缺省周五 |
| 空白日 | 无会话、无执行流水、无审定的逻辑日 |
| 审定 | 用户的一句原话，逐字转录进审定流 |
| 审定流 | 一天一个 JSONL 文件，只追加，记录用户原话 |
| 递归提议 | 对环自身规则的修改提议，带预测与到期日 |
| 生成者类 | 提议的来源分类：A 用户的目标与裁定 / B 方法与规则 / C 环本身 |
| 推送包 | 晨间投递的 JSON + 五节正文 |
| 优先级裁决 | 按五条判据给当天条目排序 |
| 施工批次 | 一次纳入多条改动、走同一条链部署的变更单位 |
| 共享源 | 各端运行时的模板源，编译后部署到各端 |
| 审计闸 | 用脚本机械判定规则是否被遵守的检查 |
| 区分力验证 | 在闸报绿之前，先证明它在该红的时候会红 |
| S / N / C | 动作风险分级：静默 / 通知 / 确认 |
